## 1. 프로젝트 구조

### 1-1. 폴더별 역할

| 폴더 | 역할 | 쓰는 기술 | 파일 수 | 상태 |
|---|---|---|---|---|
| `frontend/` | 사용자가 브라우저에서 보는 **웹 화면** 전부 | React 19, Vite, Tailwind, TypeScript | 202개 | 🟢 활발히 개발 중 |
| `backend/` | 데이터를 저장하고 꺼내주는 **서버** | NestJS, Prisma, SQLite | 130개 | 🟡 일부만 완성 |
| `mobile/` | 앱(iOS/안드로이드) 자리 | — | 1개(빈 파일) | ⚪ **미착수** |
| `docs/` | 설계 문서·기능 명세 | Markdown | 39개 | 🟢 잘 관리됨 |

용어 풀이:

- **프론트엔드** = 사용자 눈에 보이는 화면
- **백엔드** = 눈에 안 보이는 서버. 회원 정보, 병원 정보를 실제로 보관하는 곳
- **데이터베이스(DB)** = 서버가 데이터를 저장하는 창고

### 1-2. 서로 어떻게 연결되어 있나

```
[사용자 브라우저]
        |  화면을 열면
        v
[frontend  localhost:5173]        <- 화면 그리기 담당
        |  "병원 목록 주세요" 같은 요청을 보냄 (주소: /api/v1/...)
        v
[backend   localhost:3000]        <- 판단·처리 담당
        |  실제 데이터를 읽고 씀
        v
[데이터베이스  backend/prisma/dev.db]   <- 창고 (현재 SQLite라는 파일 형태)
```

- 프론트엔드가 서버를 부르는 창구는 `frontend/src/lib/apiClient.ts` **한 곳**으로 모여 있습니다. 서버 주소가 바뀌어도 여기만 고치면 됩니다 — 잘 설계된 구조입니다.
- 서버 주소는 `frontend/.env` 파일의 `VITE_API_BASE_URL` 값으로 정합니다. 개발 중에는 `http://localhost:3000/api/v1` 입니다.
- 로그인하면 서버가 **출입증(토큰)** 을 발급하고, 이후 요청마다 이 출입증을 함께 보냅니다. 출입증은 15분마다 자동 갱신됩니다.

### 1-3. mobile 폴더는 지금 어떤 상태인가

**결론: 방치된 게 아니라, 아직 시작하지 않은 빈 자리입니다.**

- `mobile/` 안에는 **0바이트짜리 README.md 파일 하나**뿐입니다. 코드가 단 한 줄도 없습니다.
- 말씀하신 "Expo를 걷어낸 흔적"은 `mobile/`이 아니라 **`frontend/` 쪽에 있습니다.** 사정은 이렇습니다:
  - 이 프로젝트는 원래 **Expo(React Native)** 라는, 웹·iOS·안드로이드를 한 코드로 만드는 기술로 시작했습니다.
  - 이후 **웹 전용으로 방향을 바꾸면서** Expo를 완전히 걷어냈습니다.
  - 그때 화면 코드 7,500줄을 전부 다시 쓰지 않으려고, 예전 방식 그대로 동작하게 해주는 **번역 레이어**를 만들어 뒀습니다 → `frontend/src/primitives/`, `frontend/src/navigation/`
  - 이건 **의도된 설계이고 정상 동작합니다.** 버려진 코드가 아닙니다. `AGENTS.md`에도 "새 화면은 이걸 안 써도 된다"고 명시돼 있습니다.
- 즉 **모바일 앱을 만들려면 지금부터 처음 시작**해야 합니다. 기존 Expo 코드를 되살리는 방식은 이미 삭제돼서 불가능합니다(git 이력에는 남아 있어 참고는 가능).

판정 기준은 네 가지입니다.

| 표시 | 뜻 |
|---|---|
| 🟢 **실제 동작** | 서버·DB와 연결되어 있음. 데이터가 진짜로 저장되고 다른 사람도 볼 수 있음 |
| 🟡 **반쪽 동작** | 화면과 기능은 되는데, **데이터가 서버가 아니라 사용자 브라우저에만 저장**됨 |

> 🟡 **"브라우저에만 저장"이 무슨 뜻인가요?**

> 2. **브라우저 기록을 지우면 사라집니다**
> 3. **병원·운영자가 그 데이터를 볼 수 없습니다** ← 사업적으로 가장 큰 문제

## 3. 백엔드(서버) 상태

### 3-1. 진짜 DB인가, 가짜인가

**진짜입니다.** 확인한 근거:

- **DB 종류**: SQLite (파일 하나로 된 가벼운 DB). 파일 위치 `backend/prisma/dev.db`, 현재 약 660KB
- **테이블 32개**가 설계되어 있음 (회원, 병원, 전문의, 상담, 찜, 후기, 알림, 커뮤니티, 약관 등)
- **초기 데이터 410행**이 실제로 들어가 있음 (직접 실행해서 확인)
- 나중에 규모가 커지면 **PostgreSQL**(더 튼튼한 DB)로 옮길 계획이 문서에 적혀 있음

> 참고: SQLite는 개발·소규모에는 충분하지만, 사용자가 많아지면 PostgreSQL로 옮겨야 합니다. 그 방법도 `docs/database/README.md`에 이미 정리돼 있습니다.

### 3-2. 회원가입·로그인이 진짜 서버에서 처리되는가

**네, 진짜입니다.** 확인한 내용:

- 회원가입하면 서버 DB에 계정이 생깁니다.
- 비밀번호는 **암호화(bcrypt)해서 저장**합니다. 원문 그대로 저장하지 않습니다. ✅
- 로그인하면 **출입증(JWT 토큰)** 을 받고, 15분마다 자동 갱신됩니다.
- **출입증 도난 방지 장치**가 들어 있습니다: 같은 갱신용 토큰이 두 번 쓰이면 공격으로 간주하고 그 계정의 모든 출입증을 폐기합니다. (수준 높은 구현입니다)
- 예전에 비밀번호가 브라우저에 그대로 저장되던 문제가 있었는데 **이미 수정됐고**, 남아 있던 옛 데이터도 앱 시작 시 자동으로 지웁니다.

**아직 안 되는 것**: 카카오/구글 로그인(버튼만 있음), 비밀번호 찾기, 로그인 시도 횟수 제한(무차별 대입 공격 방어)

## 4. 미완성 또는 문제가 있는 부분

### 4-1. 가장 중요한 문제 — 상담신청이 병원에 전달되지 않습니다

**이게 지금 이 프로젝트에서 사업적으로 가장 큰 구멍입니다.**

- 사용자가 상담 신청 버튼을 누르면 → "접수되었어요" 안내가 뜨고 → **그 데이터는 사용자 브라우저에만 저장됩니다.**
- 병원 관리자가 `/admin/consultations`를 열면 → **관리자 본인 브라우저에 있는 가짜 샘플 데이터만 보입니다.**
- 즉 **사용자와 병원이 서로 다른 창고를 보고 있어서, 실제 상담 신청은 병원에 절대 도달하지 않습니다.**

같은 이유로 **찜하기, 알림, 커뮤니티 글**도 서버로 가지 않습니다.

👉 **개발자에게 물어볼 것**: "상담·찜·알림 백엔드 API는 언제 붙나요?" — 문서상 "다음 조각"으로 계획돼 있습니다.

### 4-2. 개인정보 관련 (우선순위 높음)

## 5. 보안 점검

> 저장소가 **공개(Public)** 상태이므로 특히 중요하게 봤습니다. git에 올라간 **모든 과거 이력까지** 검사했습니다.

### 5-1. 결론: 현재 유출된 민감 정보는 없습니다 ✅

| 점검 항목 | 결과 |
|---|---|
| `.env` 파일이 현재 올라가 있는가 | ✅ **없음** |
| `.env` 파일이 **과거에 한 번이라도** 올라간 적 있는가 | ✅ **없음** (전체 커밋 이력 검사) |
| 데이터베이스 파일(`.db`)이 올라간 적 있는가 | ✅ **없음** |
| 인증서·개인키(`.pem`, `.key` 등)가 올라간 적 있는가 | ✅ **없음** |
| 소스코드에 비밀번호·API 키가 하드코딩되어 있는가 | ✅ **없음** |

> 한 번 git에 올라간 파일은 나중에 지워도 **과거 이력에 영원히 남습니다.** 그래서 "지금 없는지"가 아니라 "한 번이라도 있었는지"를 확인했고, 결과는 깨끗합니다.

### 5-2. `.gitignore` 설정: 잘 되어 있습니다 ✅

`.gitignore`는 "이 파일들은 git에 올리지 마라"고 지정하는 목록입니다. 세 곳에 있고 모두 적절합니다.

| 위치 | 막고 있는 것 |
|---|---|
| 최상위 | `.env`, `.env*.local`, `node_modules`, 빌드 결과물, `*.pem` |
| `backend/` | `.env`, `.env.*`(단 `.env.example`은 허용), **SQLite DB 파일 전부**, 로그 |
| `frontend/` | `.env`, `node_modules`, 빌드 결과물 |

특히 백엔드는 DB 파일(`prisma/*.db`)과 로그까지 꼼꼼히 막아뒀습니다. 좋은 설정입니다.

### 5-3. ⚠️ 한 가지 주의할 점 — `.env.example`에 든 예시 키

`backend/.env.example` 파일은 **의도적으로 git에 올라가 있습니다** (개발자가 무엇을 채워야 하는지 알려주는 안내 파일이라 정상입니다). 그런데 그 안에 **진짜처럼 생긴 값**이 들어 있습니다.

```
SEED_PASSWORD="mol**********"          # 시드 계정 19개의 공통 비밀번호 (평문)
JWT_ACCESS_SECRET="Evo…(64자)…79J"      # 액세스 토큰 서명 키
JWT_REFRESH_SECRET="_WP…(64자)…WkY"     # 리프레시 토큰 서명 키
```

> 값 자체는 이 문서에 옮겨 적지 않았습니다. 실제 값은 `backend/.env.example` 에 있습니다.
> 이 저장소가 공개라 **키 값과 "그 키로 무엇을 할 수 있는지"를 한자리에 모아두지 않기 위해서**입니다.
> 아래 설명을 이해하는 데 값은 필요하지 않습니다.

**지금 당장 위험하지는 않습니다.** 아직 서비스가 배포되지 않았고, 파일에도 "개발용 예시이니 운영에서는 새로 만들라"고 적혀 있습니다.

**하지만 이렇게 되면 위험합니다**: 누군가 이 파일을 그대로 복사해서 실제 서비스를 열면, **이 키가 인터넷에 공개돼 있으므로 누구나 로그인 출입증을 위조해서 아무 계정에나 들어갈 수 있습니다.**

현재 서버는 "키가 32자 이상인가, 두 키가 서로 다른가"만 검사하고, **"공개된 예시 키를 그대로 쓰고 있는가"는 검사하지 않습니다.**

👉 **개발자에게 요청할 것 (택1)**

1. (추천) 예시 키를 `여기에-직접-생성한-값을-넣으세요` 같은 안내 문구로 바꾸기
2. 운영 환경(`NODE_ENV=production`)에서 이 예시 키를 쓰면 서버가 아예 안 켜지도록 막기

### 5-4. 그 밖에 잘 되어 있는 보안 요소 ✅

- 비밀번호를 암호화해서 저장 (bcrypt)
- 관리자 화면 전체에 로그인·권한 검사 적용
- 출입증 재사용 감지 (토큰 탈취 방어)
- 로그에 비밀번호·개인정보를 찍지 않도록 명시적으로 설계 (`docs/decisions/0001-roles-and-pii.md`)
- 허용된 주소에서만 서버 호출 가능하도록 제한 (CORS)
