# 주석·문서 규칙

코드 주석은 [Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html)의 주석 절,
문서는 [Google Documentation Guide](https://google.github.io/styleguide/docguide/)(Markdown 스타일·문서 관행)와
[Google Developer Documentation Style Guide](https://developers.google.com/style)를 한국어 문서에 맞게 옮겼다.

## 무엇을 어디에 쓰나

Google 은 문서를 "코드의 이야기" 로 본다. 이야기의 각 부분이 자리가 정해져 있다.

| 무엇 | 어디 |
|---|---|
| 이 줄을 왜 이렇게 짰는지 | 코드 주석 (`//`) |
| 이 함수·타입을 어떻게 쓰는지 | JSDoc (`/** */`) |
| 이 모듈이 무엇을 책임지고 무엇을 안 하는지 | 파일 첫 JSDoc |
| 쓰는 기술과 버전 | `docs/TECH_STACK.md` |
| API 계약 | `docs/api/openapi.yaml`, `docs/api/README.md` |
| DB 설계 | `docs/database/README.md` |
| 화면 동작 | `docs/features/*.md` |
| 되돌리기 어려운 결정과 그 이유 | `docs/decisions/NNNN-제목.md` |
| 미룬 것·알려진 문제 | `backend/README.md` 미룬 것 절, `docs/features/known-issues.md` |
| 실행 방법 | 각 폴더의 `README.md` |

## 문서 관행

Google Documentation Guide 의 관행 중 이 저장소에서 지키는 것:

- **코드와 같은 커밋에서 문서를 고친다.** 나중에 고치는 문서는 고쳐지지 않는다.
- **쓸모 있는 최소한만 쓴다.** 짧고 맞는 문서가 길고 낡은 문서보다 낫다.
- **죽은 문서는 지운다.** 틀린 문서는 없는 문서보다 해롭다. 바뀐 내용은 고치고, 해결된 문제는
  해결 날짜와 함께 줄을 긋거나 지운다.
- **완벽보다 좋음.** 빠진 곳이 있어도 맞는 내용부터 올린다.
- **같은 내용을 두 곳에 쓰지 않는다.** 정본이 있는 곳으로 링크한다.

## 코드 주석

### 두 종류

- `/** ... */` — **쓰는 사람을 위한 문서.** export 하는 함수·타입·클래스, 파일 개요.
- `//` — **고치는 사람을 위한 메모.** 구현 안의 이유, 주의점. 여러 줄이어도 `//` 를 줄마다 쓴다.

### 무엇이 아니라 왜

```ts
// 나쁨 — 코드를 다시 읽어 준다
// id 로 정렬한다
orderBy: [{ rating: 'desc' }, { id: 'asc' }],

// 좋음 — 지우면 무엇이 깨지는지 말한다
// 마지막 기준이 id 여야 같은 평점끼리의 순서가 요청마다 같다.
// 흔들리면 '더 보기' 에서 병원이 두 번 보이거나 사라진다 (docs/api/README.md §5).
orderBy: [{ rating: 'desc' }, { id: 'asc' }],
```

- 코드만 읽어서는 알 수 없는 것을 쓴다: 이유, 버린 대안, 지키는 제약, 근거 문서.
- **근거의 위치를 함께 쓴다** — 계약 절(`docs/api/README.md §11`), 결정 문서, 요청서 번호, 날짜.
  이 저장소 주석의 가장 큰 장점이고, 그대로 이어 간다.
- 핵심 한 군데만 `**굵게**` 강조한다. 모든 문장을 강조하면 아무것도 강조되지 않는다.

### JSDoc

- export 하는 것에는 JSDoc 을 쓴다. 이름과 타입만으로 다 드러나는 것(`getId(): string`)은 생략해도 된다.
- **JSDoc 에 타입을 다시 쓰지 않는다.** `@param {string} id` 가 아니라 TypeScript 시그니처가 타입을 말한다.
- `@param`·`@returns` 는 이름과 타입 말고 **더할 정보가 있을 때만** 쓴다.
- 데코레이터가 있으면 JSDoc 을 데코레이터 **위에** 쓴다.
- 폐기할 것에는 `@deprecated` 와 대신 쓸 것을 적는다.

```ts
/**
 * 상담 상세. 담당 병원 관리자에게만 전체 연락처를 주고, **그 열람을 감사 로그에 남긴다.**
 * 없는 상담과 담당 밖 상담은 둘 다 `404` 다 — id 대입으로 건수가 새지 않게.
 */
@Get(':consultRequestId')
async getOne(...) { ... }
```

### 남기지 않는 것

- **변경 이력.** 누가 언제 무엇을 바꿨는지는 git 이 기록한다. 예외는 다른 브랜치에서 가져온 코드의
  출처 줄(`원작성: …, 가져와 수정 (수정한 것: …)`)이다.
- **주석 처리한 코드.** 필요하면 git 에서 꺼낸다.
- **코드와 어긋난 주석.** 코드를 바꿀 때 바로 위 주석을 함께 읽는다.

### TODO

```ts
// TODO(legal): 문구 5개 전부 법무 검토 전이다. 검토 후 이 줄을 지운다.
```

- `TODO(담당 또는 주제): 무엇을, 언제까지 또는 무엇이 되면` 형식으로 쓴다.
- 한 커밋 안에서 해결되지 않는 TODO 는 `docs/features/known-issues.md` 에도 적는다.
  코드 안의 TODO 만으로는 아무도 찾지 않는다.

## Markdown 문서

Google Markdown 스타일 가이드에서 가져온 것:

- 문서마다 `#` 제목 **하나**, 그 아래에 이 문서가 무엇인지 한두 문장.
- 제목은 `##` 같은 ATX 형식으로 쓴다. 같은 문서 안에서 제목 이름이 겹치지 않게 한다 — 링크 앵커가 된다.
- 코드 블록은 펜스(```` ``` ````)를 쓰고 언어를 적는다 (`ts`, `bash`, `json`).
- **링크 글자는 내용을 말한다.** "여기", "이 링크" 가 아니라 "[API 에러 형식](../api/README.md)".
  저장소 안의 문서는 상대 경로로 링크한다.
- 표는 정말 행·열 데이터일 때만 쓴다. 문장 몇 개를 칸에 넣을 거라면 목록이 낫다.
- 순서가 있는 절차는 번호 목록, 순서가 없으면 글머리 목록.
- 긴 문서는 위에 목차나 "한눈에 보기" 를 둔다.

## 문체

Google 개발자 문서 스타일 가이드의 원칙을 한국어에 맞게 옮겼다.

- **결론 먼저.** 판단과 규칙을 먼저 쓰고 이유를 뒤에 쓴다.
- **한 문서 안에서는 한 문체.** 설계·규칙 문서(`docs/api`, `docs/database`, 이 폴더)는 `~다` 체,
  안내 문서(`README.md`, `TECH_STACK.md`, `CODE_ANALYSIS.md`)는 `~습니다` 체를 써 왔다.
- 사용자에게 보이는 **화면 문구는 `~요` 체**다 (`'병원 정보를 찾을 수 없어요'`). 문서 문체와 섞지 않는다.
- 능동태·현재 시제·짧은 문장으로 쓴다. "~되어진다", "~할 수 있도록 한다" 대신 "~한다".
- 조건을 지시보다 먼저 쓴다: "개발 DB 를 다시 만들 거라면, 먼저 백업한다".
- 코드 요소·명령·파일 이름·값은 백틱으로 감싼다: `hospitalId`, `npm run lint`, `'booked'`.
- **날짜는 절대 날짜로 쓴다** (`2026-10-22`). "어제", "최근", "지금은" 은 읽는 날에 따라 뜻이 바뀐다.
- "간단히", "그냥", "쉽게" 를 쓰지 않는다. 읽는 사람에게 쉽지 않으면 그 단어가 상처가 된다.
- 비개발자가 읽는 문서(`CODE_ANALYSIS.md`, 요청서)는 용어를 처음 나올 때 풀어 쓴다.
