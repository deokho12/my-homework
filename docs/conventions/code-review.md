# 변경·커밋·리뷰 규칙

[Google Engineering Practices](https://google.github.io/eng-practices/)의 코드 리뷰 가이드(리뷰어용·작성자용)를
혼자 개발하는 이 저장소에 맞게 옮겼다. Google 에서는 다른 사람이 리뷰하지만, 여기서는
**셀프 리뷰 + `code-reviewer`·`qa-master` 에이전트 + 완료 게이트**가 그 자리를 대신한다 (`CLAUDE.md`).

## 리뷰의 기준

Google 리뷰어 가이드의 첫 문장이다.

> 변경이 **시스템 전체의 코드 건강을 확실히 나아지게 한다면**, 완벽하지 않아도 승인한다.

- 완벽한 코드는 없다. 더 나은 코드가 있을 뿐이다. 다듬기 때문에 진행을 막지 않는다.
- 반대로, **코드 건강을 나빠지게 하는 변경은 급해도 받지 않는다.** 나빠진 것은 쌓인다.
- 판단 순서:
  1. 기술적 사실과 데이터가 의견·취향을 이긴다.
  2. 스타일은 스타일 가이드([conventions](README.md))가 정한다. 가이드에 없는 것은 취향이다.
  3. 설계는 취향이 아니다. 근거로 따진다.
  4. 정할 규칙이 없으면 기존 코드와 일관되게 한다.

## 변경의 크기

Google 은 **작은 변경**을 강하게 권한다. 리뷰가 빨라지고, 버그가 덜 숨고, 되돌리기 쉽다.

- 대략 **100줄이면 적당하고, 1000줄이면 너무 크다** (Google 기준). 줄 수보다 "한 가지 일" 인지가 중요하다.
- **한 커밋에 한 가지 일.** 기능 변경에 리팩터링·이름 바꾸기·포맷 변경을 섞지 않는다. 섞으면 진짜 변경이 묻힌다.
- 테스트는 그 테스트가 지키는 코드와 **같은 커밋**에 넣는다.
- 커밋 하나하나가 빌드·테스트를 통과한다. 중간 커밋이 깨져 있으면 `git bisect` 를 쓸 수 없다.
- 요청서 하나는 QA 통과 후 `main` 에 올린다 (`CLAUDE.md` "커밋과 브랜치"). 요청서가 크면
  **스키마 → 계약 → 서버 → 화면** 처럼 순서대로 나눈 여러 커밋으로 만들어도 되고, push 는 QA 통과 후 한 번에 한다.

## 커밋 메시지

Google 의 변경 설명(CL description) 규칙과 이 저장소가 써 온 Conventional Commits 형식을 합쳤다.

```
<type>(<scope>): <무엇을 했는지 한 줄 요약> (request NN)

<왜 바꿨는지. 무엇이 달라지는지. 버린 대안과 남은 한계.>

<영역별 요점 — Server / Frontend / Contract / Migration>

Co-Authored-By: ...
```

### 첫 줄

- **무엇을 하는지 명령형으로** 쓴다: `add`, `move`, `fix` — `added`, `fixes` 가 아니다.
- 첫 줄만 보고도 무엇이 바뀌었는지 알 수 있어야 한다. `git log --oneline` 에서 찾게 된다.
- 기존 이력처럼 **영어**로 쓰고, 화면 문구 같은 고유 표현만 한국어로 남긴다 (`live 준비중`).
- `type`:

  | type | 언제 |
  |---|---|
  | `feat` | 사용자가 보는 동작이 생기거나 바뀐다 |
  | `fix` | 버그를 고친다 |
  | `refactor` | 동작은 그대로 두고 구조만 바꾼다 |
  | `test` | 테스트만 더하거나 고친다 |
  | `docs` | 문서만 바꾼다 |
  | `chore` | 빌드·의존성·설정 |

- `scope` 는 한쪽만 바뀔 때 쓴다 (`frontend`, `backend`). 양쪽이면 생략한다.
- 요청서에서 나온 변경이면 끝에 `(request NN)` 을 붙인다.

### 본문

- **왜**를 쓴다. 무엇은 diff 가 보여준다. 무엇을 풀려는지, 왜 이 방법인지, 무엇을 일부러 하지 않았는지.
- 미룬 것은 본문에도 적는다 (`Skipped (no consuming screen): ...`).
- 다른 브랜치에서 가져와 고친 코드는 출처 줄을 남긴다.

```
# 나쁨
fix bug
update files
phase 1

# 좋음
fix(frontend): keep the search query when going back from results

Going back from a hospital detail reset the search box because the query
lived in component state. Move it to the URL so history restores it.
```

## 셀프 리뷰 체크리스트

`code-reviewer` 에이전트를 부르기 전에, 그리고 커밋하기 전에 **diff 를 처음부터 끝까지 직접 읽는다.**
Google 리뷰어가 보는 항목 순서 그대로다.

- [ ] **설계** — 이 코드가 여기 있는 것이 맞는가? 계약과 화면 문서가 요구하는 것인가?
- [ ] **기능** — 사용자에게 의도대로 동작하는가? 빈 값·경계값·권한 없는 사용자·동시 요청은?
- [ ] **복잡도** — 지금 필요한 문제만 푸는가? Google 의 말 그대로: *"앞으로 필요할지 모른다고 추측한 문제가
      아니라, 지금 풀어야 하는 것으로 알려진 문제를 풀게 하라."*
- [ ] **테스트** — 코드가 틀리면 실제로 실패하는 테스트인가? 동작을 이름으로 썼는가?
- [ ] **이름** — 다음 사람이 설명 없이 알아듣는가? 계약의 용어와 같은가?
- [ ] **주석** — 왜를 설명하는가? 코드와 어긋난 주석은 없는가?
- [ ] **스타일·일관성** — 이 폴더의 규칙과 주변 코드를 따르는가?
- [ ] **같은 판정이 두 곳에 생기지 않았는가?**
- [ ] **문서** — 계약(`docs/api`), DB 설계(`docs/database`), 화면 문서(`docs/features`), `known-issues.md`,
      `backend/README.md`, `docs/TECH_STACK.md`(의존성이 바뀌었으면)를 같은 커밋에서 고쳤는가?
- [ ] **보안** — 비밀 키가 diff 에 없는가 (`CLAUDE.md` 안전장치 3)? 로그에 개인정보가 나가지 않는가?
- [ ] **완료 게이트** — 프론트·백엔드 양쪽에서 lint·typecheck·test·build 가 통과하는가?

## 리뷰 코멘트를 남길 때

에이전트에게 리뷰를 맡기거나, 나중에 사람이 함께 일하게 되면:

- **코드에 대해 말하고 사람에 대해 말하지 않는다.** "당신이 틀렸다" 가 아니라 "이 분기는 null 에서 실패한다".
- **이유를 함께 쓴다.** 규칙 이름만 대지 않고 왜 문제인지 쓴다.
- 꼭 고치지 않아도 되는 것은 앞에 **`Nit:`** 를 붙인다. 막는 의견과 제안을 구분한다.
- 좋은 점도 말한다.

## 작업 순서 (요약)

자세한 것은 `CLAUDE.md` 에 있다.

1. (서버 변경이면) `db-master` → `interface-master` → `backend-engineer`
2. (화면 변경이면) `designer` → `frontend-engineer`
3. `code-reviewer` — 명세 부합 검토
4. `qa-master` — 실제 동작 확인. **"QA 통과" 전에는 완료가 아니다**
5. 완료 게이트 + 비밀 키 확인 → `git fetch` 로 원격 확인 → `main` 에 커밋·push
