"이거 고장난 것 같은데" 싶을 때 여기 있는지 먼저 확인해 주세요.

여기 없는 것을 발견하셨으면 알려주세요.

> 정리된 조각 반영), 2026-10-06 일부 갱신(시술이 **분야 9개 → 세부 시술 31개** 2단 구조로 바뀐
> 조각 반영 — 병원 탐색의 `기타` 탭 항목은 그 탭이 없어져 삭제했습니다),
> 2026-10-12 일부 갱신(상담 신청 화면 개선 — 자동 채움·연락처 형식 검사·제3자 제공 동의·완료 화면,

> 섹션·관리자 문의 화면).

### 다른 사람의 알림이 보입니다

> **2026-08-19 갱신 — 찜 목록 쪽은 해결되어 이 항목에서 뺐습니다.** 예전에는 "A 계정으로 찜 →

> 로 로그인·로그아웃 양쪽에서 찜을 비우고, `useAuthStore.test.ts` 가 그 동작을 고정합니다.

> 알림은 지난 상담 이력이라 로그아웃할 때 지우면 그 계정의 기록이 사라집니다. 알림은 계정별로

> (`user` / `admin`, 화면 두 개에 대응하는 알림함)로만 가릅니다.

## 🟠 기능이 의도대로 동작하지 않는 것

### 검색으로 들어가면 홈으로 못 돌아갑니다

홈의 인기 검색어 태그를 누르면 검색 화면을 거쳐 자동으로 병원/시술 화면으로 넘어갑니다. 그다음 뒤로 가기를 누르면 검색 화면이 다시 자동 실행되어 또 앞으로 밀어냅니다. 홈으로 돌아갈 수 없습니다.

### 추천 검색어(광고) 알약이 아무것도 하지 않습니다

검색 화면 상단의 `✦` 알약 6개입니다.

- 눌러도 **검색이 실행되지 않습니다.** 검색창에 글자만 채워집니다
- 직접 검색 버튼을 눌러도 6개 중 **`교정` 하나만** 결과가 나옵니다. 나머지 5개(`몰라몰라 PICK 인기 임플란트` 등)는 `검색 결과가 없어요` 로 떨어집니다

광고 영역인데 실질적으로 죽어 있는 상태입니다.

### 의사를 검색하면 병원 화면으로 갑니다

인기 검색어의 `의사` 탭 항목을 누르면 전문의 상세 화면이 아니라 그 의사가 소속된 병원 상세로 갑니다. 전문의 상세 화면(`/doctor/:id`)이 있는데도 쓰지 않습니다.

### "전문의 상담신청"인데 어느 전문의인지 저장되지 않습니다

병원 상세나 전문의 상세에서 `전문의 상담신청` 을 눌러도, 저장되는 신청 내용에는 **병원만** 기록됩니다. 관리자가 상담을 받아도 어느 전문의를 지목했는지 알 수 없습니다.

지금은 상담 신청 폼의 `남기고 싶은 말 (선택)` 칸에 직접 적어야 합니다.

### 상담 마감인 병원도 상담이 접수됩니다

병원 상세에서는 `상담 마감` 으로 버튼이 막히지만, 상담 신청 주소로 직접 들어가면 정상 접수됩니다.

### 커뮤니티 답변을 쓸 수 있는 화면이 없습니다

답변은 샘플 데이터에만 있습니다. 사용자가 새로 쓴 글은 영구히 `아직 답변이 없어요` 상태로 남습니다.

### 커뮤니티 글 작성자가 항상 `익명` 입니다

로그인한 사람의 이름을 쓰지 않고 항상 `익명` 으로 저장됩니다. 글쓰기에 로그인 검사도 없습니다.

### 내 상담 내역에 한계가 넷 있습니다 — 화면 자체는 생겼습니다

> **2026-10-12 갱신 — "상담 신청 내역을 볼 화면이 없습니다" 는 해결되어 지웠습니다.**
> 마이페이지에 `상담 내역` 탭이 생겨(`frontend/src/pages/MyPage.tsx`) 내가 신청한 건이 최신순으로
> 보이고, 상담 신청 완료 화면의 `내 상담 내역 보기` 도 이제 빈손으로 도착하지 않습니다.
> 남은 한계 넷은 아래와 같습니다.

- **100건까지만 보입니다.** 페이지 이동 UI 가 없어 계약 상한(`pageSize` 100)만큼 한 번에 받아 전부 그립니다. 101번째부터는 조용히 사라집니다 — 다만 탭의 `상담 내역 N` 숫자는 전체를 세므로, 그때는 숫자가 목록보다 커집니다. 알림함과 같은 숙제입니다
- **줄마다 병원을 따로 조회합니다.** 로컬 상담 응답의 `hospitalName` 이 항상 `null` 이라(`features/consult/api/consultApi.ts`) 행 수만큼 `GET /hospitals/{id}` 가 나갑니다. 이름이 `—` 에서 바뀌는 순간이 보일 수 있고, 서버가 이름을 함께 내려주면 이 조회와 `useHospitalName` 훅은 사라집니다
- **`내 문의` 탭은 2026-10-12 에 실제로 동작하게 됐습니다** (요청서 `2026-10-12-03`). 숫자도 내용도 진짜입니다 — 남은 한계는 아래 "문의 기능의 한계" 를 보세요
- **확정 방문 일시가 없습니다.** `10/9(목) 14:00 방문` 줄은 자리와 서식 함수(`consultScheduleLine`)만 만들어 두고 화면은 지금 `visitAt: null` 을 넘깁니다. 병원이 일시를 입력하는 화면은 요청서 `2026-10-12-04` 의 몫입니다 — 그때 인자 하나만 바뀝니다

### 제3자 제공 동의 기록이 이 브라우저에만 남습니다

상담 신청 화면에서 받는 `[필수] 개인정보 제3자 제공 동의` 는 동의 시각과 안내문 버전을 상담 건에
함께 저장하지만, **그 저장소가 브라우저입니다.** 브라우저 데이터를 지우면 동의 기록도 함께
사라지고, 회사가 분쟁 시 꺼내 볼 수 있는 기록이 아닙니다. 서버의 상담 기능이 생겨야 증빙이 됩니다.

### 동의 안내문이 법무 검토 전이고, 보유 기간이 `[확정 필요]` 인 채로 사용자에게 보입니다

`자세히` 팝업의 다섯 항목 전부 법무 검토를 받지 않았습니다. 특히 네 번째 `보유·이용 기간` 은
회사가 기간을 정하지 않아 **`[확정 필요] 회사에서 보유 기간을 확정하는 대로 안내드릴게요.` 가
사용자 화면에 그대로 노출됩니다.** 출시 전에 실제 기간으로 교체해야 합니다
(`frontend/src/features/consult/content/thirdPartyConsentNotice.ts` 의 `TODO(legal)`).

### 동의 안내문만 다른 곳에 있습니다

`이용약관`·`개인정보처리방침`은 약관 화면에서 보는데, 제3자 제공 안내문은 앱 코드 안의 문구
상수입니다 (`GET /legal-documents/{slug}` 로 내려오지 않습니다). 문구를 고치려면 개발자가 코드를
고치고 버전을 올려야 하고, 사용자가 나중에 "내가 동의한 문구"를 다시 찾아볼 화면도 없습니다.

### 샘플 상담 알림 두 개를 눌러도 이동하지 않습니다

알림함의 `상담 상태 변경` 알림은 "내 상담 내역"에서 그 상담의 병원을 찾아 이동합니다.
상담이 **계정별로 나뉘면서**(다른 계정이 남긴 번호가 자동 채움에 뜨지 않도록 한 변경) 주인이
없는 샘플 상담 7건은 누구의 내역에도 잡히지 않습니다. 그래서 샘플 알림 중 `cr2`·`cr3` 을
가리키는 두 개는 **읽음 처리만 되고 병원 화면으로 넘어가지 않습니다.** 내가 직접 신청한
상담의 알림은 정상적으로 이동합니다.

### 문의 기능의 한계 — 화면 셋은 모두 동작합니다

2026-10-12 에 [문의하기](inquiry.md)·병원 상세 `문의` 섹션·[관리자 문의 화면](admin-inquiries.md)이 생겼습니다.
**서버에는 아직 문의 기능이 없어서** 상담·찜과 같은 방식(브라우저 저장)으로 먼저 만들었고, 그래서 남는 한계가 다음과 같습니다.

- **문의도 답변도 이 브라우저 안에만 저장됩니다.** 다른 컴퓨터·시크릿 창에서는 보이지 않고, 브라우저 데이터를 지우면 사라집니다. 실제로 병원에 전달되지도 않습니다
- **문의 샘플 데이터가 없습니다.** 모든 병원이 처음에는 `아직 공개된 문의가 없어요` 입니다. 샘플을 넣으려면 `frontend/src/mocks/fixtures/` 가 자연스러운 자리인데 **그 폴더는 백엔드 seed 가 그대로 import 하는 원본**이라, 서버에 없는 테이블의 가짜 행을 넣지 않았습니다
- **답변 알림에 받는 사람이 없습니다.** 알림이 `audience=user` 로만 저장되어, 같은 브라우저의 다른 계정으로 로그인해도 `문의에 답변이 왔어요` 가 보입니다 (위 🔴 "다른 사람의 알림이 보입니다" 와 같은 뿌리입니다). 알림을 눌러 열리는 `내 문의` 탭은 계정별로 갈려서 **질문 본문과 나머지 답변은 보이지 않지만**, 알림 줄 자체에 `{병원명} · 답변 앞 60자` 가 적혀 있어 **그 60자는 같은 브라우저의 다른 계정에게도 읽힙니다** (비공개로 답한 건도 마찬가지입니다). 알림에 받는 사람이 생겨야 닫힙니다
- **문의자 이름을 문의 행에 적어 둡니다.** 서버는 `users.name` 을 조인해 마스킹하고 이름 스냅샷을 두지 않기로 했는데(`docs/api/README.md` §4), 로컬에는 사용자 표가 없어 **작성 시점의 이름**을 저장합니다. 계정 이름을 바꿔도 관리자 화면에는 옛 이름의 마스킹(`김*준`)이 남습니다. 병원 이름도 같은 이유로 작성 시점 값입니다 (답변 알림 문구에 병원명이 필요합니다)
- **관리자 문의 목록은 100건까지만 보입니다.** 페이지 이동 UI 가 없어 계약 상한만큼 한 번에 받습니다. 탭의 숫자는 전체를 세므로, 101건을 넘으면 숫자가 목록보다 커집니다 (상담 목록·알림함과 같은 숙제입니다)
- **병원 상세의 공개 Q/A 도 20건까지만 받아옵니다.** `문의 더보기` 는 **받아온 목록을 펼칠 뿐** 다음 쪽을 더 불러오지 않습니다. 21번째부터는 `문의 N건 · 답변 N` 의 숫자에는 들어가지만 목록에는 나오지 않습니다
- **답변은 수정·삭제할 수 없고, 문의도 취소할 수 없습니다.** 일부러 그렇게 두었습니다 (답변이 조용히 바뀌면 `문의에 답변이 왔어요` 알림이 거짓이 됩니다). 신고·숨김 경로도 없습니다
- **도배를 막는 규칙이 없습니다.** 같은 사람이 같은 병원에 연속으로 문의할 수 있습니다. 서버의 요청 한도가 1차 방어선인데 서버가 아직 없습니다
- **관리자 문의 화면에 병원별 필터가 없습니다.** 담당 병원이 여러 곳이면 한 목록에 섞여 나오고, 목록 항목에 병원 이름이 보이지 않습니다 (계약에는 `hospitalId` 필터가 있습니다 — 화면만 아직 없습니다)
- **주제별 필터도 화면에 없습니다.** 계약에는 있습니다
- **인가가 진짜가 아닙니다.** "담당 병원만 보인다"·"운영자는 답변할 수 없다" 는 판정을 프론트의 api 계층이 흉내 낸 것이라, 브라우저 안에서 상태를 고치면 뚫립니다. 서버가 생겨야 닫히는 구멍이고, 상담·찜도 같은 상태입니다

### 지도가 보이지 않습니다

카카오맵 API 키가 설정되지 않아서 지도 자리에 `카카오맵 API 키가 설정되지 않았어요` 만 표시됩니다. 병원 탐색의 지도 보기, 병원 상세의 지도 창 모두 해당합니다.

### 시술 분야 세 곳은 광고 병원이 위로 안 올라가고 100곳까지만 보입니다

`충치치료` · `심미` · `턱관절·스플린트` 에서 **`전체`** 를 보고 있을 때입니다. 병원 탐색의 그
세 탭, 그리고 시술 카테고리 화면에서 `전체` 알약을 고른 경우 모두 해당합니다.

- **광고 병원이 맨 위로 올라가지 않습니다.** `광고` 배지는 그대로 붙지만 순서는 일반 정렬(인기순 등) 그대로입니다
- **병원이 100곳까지만 나옵니다.** 지금 병원이 11곳뿐이라 보이지 않지만, 늘면 101번째부터 조용히 빠집니다

세부 시술을 하나 고르면(`레진` `크라운` …) 두 제약이 모두 사라집니다. 나머지 분야
(`임플란트` `교정` `잇몸치료` `보톡스` `사랑니·발치`)도 영향이 없습니다.

**이유:** 서버의 병원 목록 API 는 시술을 **한 번에 하나만** 받습니다. 위 세 분야는 서버 시술
여러 개(충치치료 = 충치치료·인레이·크라운)에 걸쳐 있어서 한 번의 요청으로 거를 수 없고,
넉넉히(100곳) 받아 화면에서 다시 거릅니다. 광고 우선 노출은 서버가 시술 하나를 받았을 때만
켜지는 규칙이라 이 경로에서는 꺼집니다. 서버가 분야 단위 필터를 갖게 되면 사라지는 제약입니다.

## 🟡 관리자 화면 — 데이터가 잘못될 수 있는 것

### 병원 정보 수정에서 대표 이미지를 바꿔도 병원 상세 사진이 그대로입니다

병원 정보 **수정** 화면에서 대표 이미지 주소를 바꿔도 병원 상세 화면의 사진 캐러셀에는 반영되지
않습니다. 캐러셀(`Hospital.images`)과 대표 이미지(`Hospital.thumbnail`)가 서로 다른 필드이고,
수정 화면은 의도적으로 `images` 를 건드리지 않기 때문입니다 — 여러 장의 진짜 사진을 가진 병원의
갤러리를 대표 이미지 한 장으로 덮어쓰는 사고를 피하려는 것입니다. 캐러셀을 직접 편집하는 화면이
생기기 전까지 남는 한계입니다.

> **2026-08-14 갱신 — 신규 등록은 해결됐습니다.** 등록 화면은 이제 대표 이미지 값을
> `images: [thumbnail]` 로 캐러셀에도 함께 넣습니다(대표 이미지를 비워도 화면이 쓰는 플레이스홀더
> 이미지가 들어가 캐러셀이 비지 않습니다). 위 증상은 **수정** 화면에만 남아 있습니다.

### 인증된 전문의의 전문 분야를 바꿔도 재검수되지 않습니다 — 해결됨

승인된 전문의의 전문 분야를 다른 과로 바꾸면 인증 상태가 `대기` 로 되돌아가고, 새 과의 검수를 다시 받아야 배지가 노출됩니다.

### 전문의 승인/반려 결과가 병원에 통보되지 않습니다 — 절반만 해결됨

전문의 인증을 승인·반려하면 이제 서버가 그 병원 담당자 전원에게 알림 행을 만듭니다. 다만 **알림함
화면이 아직 그 알림을 읽어오지 않습니다** — 알림함은 여전히 예전 방식(브라우저 저장)을 쓰고
있어서, 병원 담당자에게는 지금도 검수 결과가 화면에 보이지 않습니다. 알림함이 서버 알림을 읽어오면
자동으로 완성됩니다.

### 같은 상태를 다시 눌러도 처리됩니다 — 해결됨

이미 `예약완료` 인 상담에 `예약완료` 를 다시 눌러도 이제 **아무 일도 일어나지 않습니다.** 상태 변경 기록도, 사용자 알림도 늘지 않습니다. 목록의 빠른 상태 버튼을 오탭해도 안전합니다.

> **2026-08-19 갱신.** `frontend/src/features/consult/api/consultApi.ts` 의 `updateConsultStatus`
> 가 현재 상태와 같은 값을 받으면 저장도 알림 생성도 하지 않고 그대로 돌려줍니다(no-op).
> `consultApi.test.ts` 의 "같은 상태로 다시 부르면 이력도 알림도 늘지 않는다 (no-op)" 케이스가 그
> 동작을 고정합니다. 화면(`screens/admin/consultations/index.tsx`)에서 버튼을 따로 막지 않는
> 이유는 같은 판정을 두 곳에 두지 않기 위해서입니다 — 판정은 한 군데(api)에만 있습니다.

### 미승인 전공을 가진 전문의가 있는 병원에는 새 전문의를 추가할 수 없습니다

병원에 검수 대기 중이거나 반려된 전문의가 한 명이라도 있으면, 그 병원에 새 전문의를 추가하는 저장이
막힙니다. **화면(관리자 병원 폼)이 저장 버튼 자체를 비활성화해서 막는 것**이고, 요청이 서버까지
가지도 않습니다 — 관리자가 미승인 전공을 대신 지어내 보낼 방법이 없기 때문입니다(전문의 로스터를
통째로 교체하는 저장 방식이라 모든 항목에 전공이 필요합니다). 기존 전문의의 정보 수정·삭제는
영향받지 않습니다 — 새로 추가할 때만 막힙니다.

### 두 전문 분야는 전문의 등록 시 시술이 자동으로 채워지지 않습니다

`소아치과전문의` · `구강악안면방사선과전문의` 로 새 전문의를 등록하면서 담당 시술을 직접 고르지
않으면, 그 전문의의 시술 목록이 **에러 없이 조용히 0건**이 됩니다. 이 두 전공이 시술 자동 매핑
표에 아직 없기 때문입니다. 제품 쪽에서 두 전공에 시술을 배정하기 전까지는 등록할 때 시술을
직접 선택해 주세요.

샘플 상담 데이터의 날짜가 2026년 6~7월이라 현재 월과 맞지 않습니다.

### 화면에 보이는 시술 이름이 서버에 저장된 이름과 다릅니다

홈·병원 탐색·시술 카테고리·병원 상세·관리자 병원 폼은 **시술 분야 9개 → 세부 시술 31개**
체계([시술 카테고리 문서](category.md))를 쓰는데, 서버가 아는 시술은 아직 13개뿐입니다.
그 13개를 세부 시술로 다시 이름 붙이면서 여섯 개가 달라졌습니다.

| 서버에 저장된 이름 | 화면에 보이는 이름 |
|---|---|
| 충치치료 | 레진 |
| 교정 | 일반(브라켓)교정 |
| 보톡스 | 이갈이 보톡스 |
| 턱관절 | 턱관절장애 치료 |
| 사랑니 | 사랑니 발치 |
| 잇몸치료 | 잇몸치료 (분야 이름과 세부 시술 이름이 같습니다) |

- 같은 하나를 가리키는 두 이름입니다. 관리자가 `레진` 을 체크하면 서버에는 `충치치료` 로 저장되고, 사용자 화면에는 다시 `레진` 으로 보입니다.
- **세부 시술 31개 중 18개는 `준비중` 이라 저장할 수 없습니다.** 관리자 폼에서 회색으로 보이고 눌리지 않습니다. 서버가 그 시술을 모르기 때문입니다.
- **`스케일링·예방` 분야는 세부 시술 4개가 전부 준비중이라 병원이 구조상 0곳입니다.** 홈 격자 카드에 `준비중` 이 붙고, 병원 탐색 탭과 카테고리 화면에서는 서버에 물어보지도 않고 `등록된 병원이 아직 없어요` 를 보여줍니다.

### 커뮤니티 질문하기·관리자 상담 화면의 시술 이름만 옛 목록을 씁니다

커뮤니티 질문하기, 관리자 상담 목록·상세는 여전히 **서버 시술 13종**의 이름을 그대로
보여줍니다. 홈·탐색·시술 카테고리·병원 상세가 쓰는 분야 9개 체계와 **다른 목록**이라,
같은 시술이 커뮤니티에서는 `충치치료`, 병원 카드에서는 `레진` 으로 보입니다.

의도적으로 바꾸지 않았습니다 — 이 화면들은 "어떤 시술로 문의하는가"를 적는 곳이라 분야
단위보다 서버가 아는 단위가 맞고, 한 번에 다 바꾸면 되돌릴 범위가 커집니다. 서버가 분야
체계를 네이티브로 갖게 되면 자연히 하나가 됩니다.

> **2026-10-12 갱신 — 상담 신청 화면과 마이페이지 상담 내역은 여기서 빠졌습니다.** 둘 다 이제
> `충치치료 · 레진` 처럼 `분야 · 세부시술` 로 보여줍니다(서버에 보내는 값은 그대로 13종 중
> 하나이고, 두 화면이 같은 함수 `features/consult/consultDisplay.ts` 를 씁니다).
> 그래서 **같은 상담이 신청자 쪽 화면에서는 `충치치료 · 레진`, 관리자 목록에서는 `충치치료` 로
> 다르게 보입니다.**

### `/explore?category=<옛 시술 id>` 는 분야 전체로 넓어집니다

북마크해 둔 `/explore?category=crown` 같은 옛 주소로 들어오면 그 시술이 속한 **분야**
(`충치치료`) 탭이 선택됩니다. 크라운만 보던 목록이 레진·인레이까지 포함된 목록으로 넓어지고,
**주소창의 `category=crown` 은 그대로 남아** 주소와 화면이 달라 보입니다.

세부 시술까지 그대로 살리려면 `/category/cavity?sub=crown` 을 쓰세요. 홈·검색·꿀팁 CTA 는
이미 그 주소로 보냅니다.

## ⚪ 사소한 것

- **뒤로 가기 버튼이 두 개** — 전문의 상세, 시술 꿀팁 상세에서 화면 상단 헤더의 `‹` 와 화면 안 동그란 버튼이 같이 나옵니다. 두 화면의 헤더 제목도 항상 비어 있습니다
- **이벤트 화면에서 두 번째 줄 카드가 붙습니다** — 카드 사이 위아래 여백이 없습니다
- **커뮤니티 조회수가 방문마다 올라갑니다** — 같은 사람이 다시 봐도 계속 증가해서 실제 조회 수와 무관합니다
- **홈 배너를 눌러도 반응이 없습니다** — 링크가 없는 것이 현재 정상 동작입니다. 자동 넘김도 없습니다
- **광고 노출 기간이 2026년 7~9월로 고정** — 그 기간이 지나면 `광고` 배지와 상단 노출이 조용히 사라집니다
- **`주요 진료 분야` 가 비면 제목만 남습니다** — 전문의 상세에서, 다른 영역들은 `등록된 ... 없어요` 안내가 있는데 이 영역만 없습니다
- **앱 다운로드 QR과 스토어 주소가 비어 있습니다** — 홈 화면 하단. 회색 `QR` 상자만 나옵니다
- **회사 정보가 전부 임시 값입니다** — 대표 `홍길동`, 개인정보관리책임자 `김보안` 등. `frontend/src/mocks/fixtures/placeholder-company-info.ts` 의 값을 바꾸면 홈 화면 하단에 반영됩니다
- **찜 하트 버튼에 이름이 없습니다** — 병원 카드·병원 상세의 ❤️/🤍 는 그림 글자뿐이라 화면 낭독기가 "찜하기"인지 알 수 없게 읽습니다 (`HospitalCard.tsx`, `HospitalDetailView.tsx`). 2026-10-12 마이페이지 QA 에서 발견한 기존 문제입니다
- **마이페이지의 `준비중` 메뉴 글자가 매우 흐립니다** — `알림 설정`·`회원정보 수정` 은 누를 수 없는 줄이라 일부러 옅게 칠했지만, 흰 바탕 대비가 낮아 눈이 불편한 분께는 잘 안 보일 수 있습니다. 오른쪽 `준비중` 배지로 상태는 전달됩니다

## 개발자용 메모

문서에는 쓰지 않았지만 구조 개편 때 함께 다뤄야 하는 것들입니다.

- **저장소 갈라짐 위험 — 해소됨.** 병원·전문의는 실제 백엔드(`hospitalApi`/`doctorApi`, TanStack Query)를 쓰고, 아직 서버가 없는 넷(상담·찜·알림·커뮤니티)은 `frontend/src/lib/localCollection.ts` **한 파일**로 모였습니다(브라우저 저장). 예전의 `mockDb`(`src/mocks/db.ts`)와 도메인별 zustand 스토어(`useConsultStore`·`useFavoritesStore`·`useNotificationStore`·`useCommunityStore`)는 삭제됐습니다 — 같은 데이터를 두 저장소가 각자 들고 있어 저장 한 번이 갈리던 회귀 패턴의 원인이었습니다. 지금은 화면 → 훅(`features/*/hooks`) → 계약 함수(`features/*/api`) → `localCollection` 순으로 한 줄이고, 서버가 생기면 api 함수 본문만 `apiRequest(...)` 로 바꾸고 `localCollection.ts` 를 지우면 됩니다
- **`PATCH /notifications/{id}/read` 의 404 코드는 프론트가 임의로 정했습니다** — `docs/api/openapi.yaml` 이 이 응답의 `code` 를 예시로 고정하지 않아, 로컬 구현(`features/notification/api/notificationApi.ts`)이 `NOTIFICATION_NOT_FOUND` 를 씁니다. **백엔드도 같은 이름을 쓰면 프론트는 손댈 곳이 없습니다.** 다른 이름을 쓰기로 정하면 그 파일 한 곳만 맞추면 됩니다 — 지금은 어느 화면도 이 코드로 분기하지 않습니다(읽음 처리는 조용히 실패합니다)
- **관리자 알림 이동이 종류를 구분하지 않음** — `frontend/src/screens/admin/notifications.tsx:30` 이 `relatedId` 만 보고 상담 상세로 보냅니다. 전문의 인증 알림도 이제 서버에 만들어지지만, 이 화면은 아직 서버 알림을 읽지 않으므로 현재는 도달하지 않는 경로입니다 — 알림함이 서버로 옮겨가면 함께 고쳐야 합니다
- **알림함은 100건까지만 보입니다** — 두 알림함 화면이 `pageSize: 100`(계약 상한)으로 한 번에 받아 전부 그립니다. 알림은 상담 접수·상태 변경마다 늘기만 하는 컬렉션이라 언젠가 101번째부터 조용히 사라집니다(안 읽은 개수 배지는 전체를 세므로 목록에 없는 알림이 숫자에만 남습니다). 페이지 이동 UI 나 무한 스크롤이 그 시점의 숙제입니다
- **상담 도메인은 계약이 구현보다 앞서 있습니다** — `docs/api/openapi.yaml` 에는 `POST /consult-requests` 가 `thirdPartyConsent`·4지선다 `ConsultPreferredTime`·`422 THIRD_PARTY_CONSENT_REQUIRED`·`422 VALIDATION_FAILED(INVALID_PHONE_FORMAT)` 까지 적혀 있지만 **백엔드에 상담 모듈이 아직 없습니다.** 프론트의 `features/consult/api/consultApi.ts` 가 그 계약을 흉내 내어(같은 코드·같은 문구·같은 정규식·연락처 `010-1234-5678` 정규화) 브라우저 저장소에 씁니다. 서버가 생기면 함수 본문만 `apiRequest(...)` 로 바뀌어야 하고, **화면과 테스트는 그대로여야 합니다** — 그러지 않으면 계약을 흉내 낸 의미가 없습니다
- **로컬 상담에만 `ownerUserId` 라는 저장 전용 필드가 있습니다** — `lib/localCollection.ts` 의 `StoredConsultRequest`. 서버라면 토큰으로 알아낼 "누가 신청했는가" 를 로컬에서는 행에 적는 수밖에 없어서 둔 것이고, `fetchMyConsultRequests` 만 봅니다. 응답 투영에서 떼어내므로 화면·도메인 타입에는 나타나지 않습니다. 서버 전환 시 이 필드와 `currentUserId()` 헬퍼를 함께 지웁니다
- **문의 도메인도 계약이 구현보다 앞서 있습니다** — `docs/api/openapi.yaml` 의 `hospital-inquiries` 7개 오퍼레이션 전부 백엔드에 없습니다. 프론트의 `features/inquiry/api/inquiryApi.ts` 가 같은 코드·같은 문구(`HOSPITAL_INQUIRY_NOT_FOUND`, `OPERATOR_CANNOT_ANSWER`, `INQUIRY_ALREADY_ANSWERED`, `VALIDATION_FAILED` + `details[]`)로 흉내 내어 브라우저 저장소에 씁니다. 서버가 생기면 함수 본문만 `apiRequest(...)` 로 바뀌어야 하고 화면·테스트는 그대로여야 합니다. **계약과 갈리는 두 곳은 파일 머리말에 적어 두었습니다**: 병원 존재 확인(`404 HOSPITAL_NOT_FOUND`)을 하지 않는 것과, 문의자·병원 이름을 행에 적어 두는 것
- **문의 행에도 로컬 전용 필드가 셋 있습니다** — `lib/localCollection.ts` 의 `StoredHospitalInquiry.ownerUserId`·`askerDisplayName`·`hospitalName`. 전부 서버라면 토큰·조인으로 얻는 값이고 응답 투영에서 떼거나 마스킹해서 내보냅니다. 서버 전환 시 `currentUser()` 헬퍼와 함께 지웁니다
- **공개 판정과 상태 판정은 순수 함수 두 개입니다** — `features/inquiry/inquiryVisibility.ts`. 계약(`docs/api/README.md` §14)이 서버에도 같은 모양(`hospital/inquiry-visibility.ts`)을 요구합니다. **백엔드가 이 둘을 각자 구현하면 비공개 문의가 공개 목록에 뜰 수 있습니다** — 규칙 문장을 그대로 옮겨 주세요
- **이름 마스킹 함수는 `frontend/src/utils/pii.ts` 하나입니다** — 지금은 문의 api 만 부릅니다. 상담의 `operator` 마스킹은 서버 몫이라 로컬에 구현이 없고, 서버가 생기면 둘 다 서버가 합니다
- **`RouterBridge` 가 렌더 중 모듈 변수 대입** — `navigation/index.tsx:57`. 의도된 shim 이지만 React 19 동시성 렌더에서 위험한 패턴입니다
- **`HospitalForm` 이 React Hook Form 을 쓰지 않습니다** — `frontend/CLAUDE.md` 는 폼 상태를 RHF 로 관리하라고 규정하지만 `components/admin/HospitalForm.tsx`(600여 줄)는 여전히 `useState` 를 씁니다. 주소 검색 연동 + 동적 전문의 로스터 편집이 얽힌 폼이라, 목 제거가 목적이었던 지난 작업 범위에서 RHF 이관은 의도적으로 미뤘습니다(회귀 위험). 코드 동작에는 영향이 없지만 조용히 넘어가지 않도록 여기 기록해 둡니다
- **관리자 문의의 답변칸도 RHF 가 아닙니다** — `features/inquiry/components/AdminInquiryDetail.tsx` 는 답변 초안을 페이지(`AdminInquiriesPage`)의 `useState` 로 들고 내려줍니다. 초안이 **목록↔상세 전환(CSS 로만 가리는 구조)과 선택 변경 확인창**보다 오래 살아야 해서 폼 바깥에 둔 것이고, 검사 자체는 사용자 문의 폼과 같은 zod 스키마(`inquiryAnswerSchema`)가 합니다. 사용자 쪽 문의 폼(`InquiryForm`)은 규정대로 RHF 를 씁니다
- **전공 배지 규칙(FE)과 전문의 시술 자동 배정(BE)이 서로 다른 표입니다** — 프론트의 `frontend/src/utils/specialty.ts` `CATEGORY_SPECIALTIES`(분야 → 강조할 전공들)와 백엔드의 `backend/src/doctor/specialty-procedures.ts`(전공 → 자동 배정할 시술들)가 일치하지 않습니다. `implant` 는 BE 가 치과보철, FE 가 구강악안면외과이고, `whitening`·`cavity` 는 BE 가 통합치의학만, FE 는 [치과보철, 통합치의학] 둘 다입니다. **용도가 달라서(한쪽은 배지 강조, 한쪽은 등록 시 기본값) 지금은 버그가 아니지만**, 백엔드가 분야 체계를 네이티브로 가질 때 둘을 한 표로 맞출지 재검토해야 합니다
- **`frontend/src/mocks/fixtures/procedures.ts` 는 여전히 백엔드 seed 의 원본입니다** — `backend/prisma/seed/fixtures.ts:31` 이 이 파일을 import 합니다. 그래서 분야 체계 작업에서 **1바이트도 건드리지 않았습니다.** 대신 `frontend/src/features/procedure/taxonomy.test.ts` 가 `LEGACY_TO_SUB` 의 키 집합과 이 fixture 의 id 집합이 같은지 검사해서, 서버가 시술을 추가·삭제하면 테스트가 먼저 깨지도록 묶어 두었습니다
- **백엔드 인계 — 시술 분야를 서버가 직접 갖게 될 때 할 일** (지금은 프론트에만 있는 매핑 계층입니다):
  1. `ProcedureCategory` 테이블(9행) + `Procedure.categoryId` FK + **세부 시술 18행 추가** + 준비중 플래그
  2. `GET /procedures` 응답에 `categoryId` (또는 `GET /procedure-categories`)
  3. `GET /hospitals` / `GET /doctors` 에 `categoryId=` 또는 반복 `procedureId=` → Prisma `{ in: [...] }`; `categoryId` 가 있을 때도 광고 우선 노출을 켤 것
  4. `backend/src/doctor/specialty-procedures.ts` 에 새 18개 id 추가 + `implant` 전공 재검토 (FE 는 구강악안면외과로 보고 있습니다)
  5. `docs/api/openapi.yaml` 의 `ProcedureId` enum 확장 + `categoryId` 파라미터
  6. seed 의 시술 원본을 `frontend/src/mocks/fixtures/procedures.ts` 에서 `backend/prisma/seed/data/` 로 이전
  → 그 뒤 프론트는 `legacyProcedureId` 를 그냥 id 로 쓰고, 클라이언트 필터 분기를 지우고, 관리자 폼의 31개를 전부 활성화하면 됩니다
