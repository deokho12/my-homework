## 🟠 기능이 의도대로 동작하지 않는 것

### 검색으로 들어가면 홈으로 못 돌아갑니다

홈의 인기 검색어 태그를 누르면 검색 화면을 거쳐 자동으로 병원/시술 화면으로 넘어갑니다. 그다음 뒤로 가기를 누르면 검색 화면이 다시 자동 실행되어 또 앞으로 밀어냅니다. 홈으로 돌아갈 수 없습니다.

### 추천 검색어(광고) 알약이 아무것도 하지 않습니다

검색 화면 상단의 `✦` 알약 6개입니다.

- 눌러도 **검색이 실행되지 않습니다.** 검색창에 글자만 채워집니다(그 글자로 추천 목록은 뜹니다)
- 직접 검색 버튼을 눌러도 6개 중 **`교정` 하나만** 결과가 나옵니다. 나머지 5개(`몰라몰라 PICK 인기 임플란트` 등)는 `검색 결과가 없어요` 로 떨어집니다 — 문구가 시술·병원 이름보다 길어서 추천 목록도 비어 있습니다

광고 영역인데 실질적으로 죽어 있는 상태입니다.

### 검색 추천 목록의 한계

입력 중 추천(`시술`/`병원`/`원장님`)은 **서버에 통합 검색 엔드포인트가 없어서** 화면이 여러
요청을 조합해 만듭니다. 그래서 남는 것들입니다.

- **입력이 한 번 멈출 때마다 최대 7개의 요청이 나갑니다.** 병원·전문의 이름 조회 2개, 직함이
  붙은 검색어의 재조회 1개, 걸린 시술로 하는 병원·전문의 조회 2개, 원장님 줄의 소속 병원 이름
  조회 최대 3개입니다. 키 입력마다가 아니라 **멈출 때마다** 이고(250ms 디바운스 · 최소 2자 ·
  30초 캐시), 전형적으로는 2~5개입니다. 병원이 수백 곳이 되면 입력 중 가장 비싼 요청이 됩니다
- **원장님 줄의 병원 이름을 줄마다 따로 조회합니다.** `Doctor` 응답에 병원 이름이 없어서
  `GET /hospitals/{id}` 가 행마다 나갑니다(같은 병원이면 한 번). 조회 중에는 `—` 로 보입니다 —
  마이페이지 상담 내역·관리자 상담 목록이 이미 같은 이유로 같은 훅(`useHospitalName`)을 씁니다
- ~~**`충치치료`·`심미`·`턱관절·스플린트` 가 걸리는 검색어는 추천 한 번에 100건짜리 응답을
  병원·전문의 각 1개씩 받습니다.**~~ — 해결됨 (2026-10-21, 요청 14). 서버가 분야로 거를 수 있게 되어
  어느 분야든 한 번 묻고 20건 단위로 받습니다
- **추천 목록은 그룹당 3개까지입니다.** "더 보기"가 없어 4번째부터는 보이지 않습니다. 여러
  결과를 나란히 펼쳐 보려면 검색 결과 목록 화면이 따로 필요합니다
- **Tab 을 눌러도 추천 목록이 접히지 않습니다.** 떠 있는 드롭다운이 아니라 인기 검색어가 있던
  자리를 대신하는 영역이라, 포커스가 떠나도 그대로 둡니다. 접으려면 Esc 를 누르면 됩니다
- **`?q=` 는 화면에 들어오는 순간에만 읽습니다.** 이미 검색 화면에 있는 상태에서 같은 화면의
  다른 `?q=` 주소로 이동하는 경로는 지금 없습니다

### "전문의 상담신청"인데 어느 전문의인지 저장되지 않습니다

병원 상세나 전문의 상세에서 `전문의 상담신청` 을 눌러도, 저장되는 신청 내용에는 **병원만** 기록됩니다. 관리자가 상담을 받아도 어느 전문의를 지목했는지 알 수 없습니다.

지금은 상담 신청 폼의 `남기고 싶은 말 (선택)` 칸에 직접 적어야 합니다.

### 상담 마감인 병원도 상담이 접수됩니다

병원 상세에서는 `상담 마감` 으로 버튼이 막히지만, 상담 신청 주소로 직접 들어가면 정상 접수됩니다.

### 커뮤니티 답변을 쓸 수 있는 화면이 없습니다

답변은 샘플 데이터에만 있습니다. 사용자가 새로 쓴 글은 영구히 `아직 답변이 없어요` 상태로 남습니다.

### 커뮤니티 글 작성자가 항상 `익명` 입니다

로그인한 사람의 이름을 쓰지 않고 항상 `익명` 으로 저장됩니다. 글쓰기에 로그인 검사도 없습니다.

서버라면 상담 행에서 병원을 조인해 얻을 값이지만, 브라우저 저장에는 병원 표가 없어
**상태를 바꾼 화면(관리자 상담 상세)이 이름을 함께 넘겨줍니다**
(`ConsultStatusUpdateInput.hospitalName` — 계약에 없는 로컬 전용 입력입니다).
다른 통로로 상태가 바뀌면 이름이 비고, 그때 문구는 `병원 · …` 으로 나옵니다 (틀린 이름을
적는 대신 비워 둡니다). 서버가 알림을 만들기 시작하면 이 입력은 사라집니다.

### 예전에 받은 상담 알림은 `상담` 아이콘으로 보입니다

알림 줄 왼쪽의 종류 아이콘(예약·상담·문의·이벤트·안내)은 알림에 적힌 **변경 후 상태**로
가릅니다. 2026-10-13 이전에 만들어진 알림과 샘플 알림에는 그 칸이 없어서, 예약확정 알림이었어도
달력(예약) 아이콘 대신 **상담 아이콘**을 받습니다. 과거 행을 채워 넣지 않는 이유는 옛 문구가
`상담 상태가 '예약완료'(으)로 변경되었어요` 라서, 예약 아이콘을 붙이면 보내지 않은 말을
지어내는 셈이기 때문입니다.

### 예약 알림이 "병원에 전화해 주세요" 라고 하는데, 앱에 병원 전화번호가 없습니다

예약확정·예약 일시 변경 알림은 요청서 08 문구대로 `변경이 필요하면 병원에 전화해 주세요` 로
끝납니다. 그런데 **병원 데이터에 전화번호 칸이 아직 없어서** 병원 상세·카드·알림 어디에도 번호가
보이지 않습니다. 환자는 번호를 앱 밖에서 찾아야 합니다. 전화번호 칸은 요청서 06(병원 관리자 직접
가입)의 데이터 설계에서 처음 생깁니다(`docs/database/README.md` §14.2). 환자 화면에도 **공개하기로
요청자가 정했고**(2026-10-21), 공공데이터에서 대표번호를 받아 오는 **요청서 17** 과 직접 가입의
**요청서 18** 에서 반영합니다.

### 찜한 병원의 새 이벤트 알림은 아직 없습니다

요청서 08 에 적힌 "찜한 병원의 새 이벤트" 알림은 **미뤘습니다.** 이벤트를 만들고 관리하는
기능 자체가 없어서(이벤트 알림은 샘플 한 건뿐입니다) 알릴 사건이 생기지 않습니다. 이벤트
기능이 생기는 날 함께 만듭니다.

### 문의 기능의 한계 — 화면 셋은 모두 동작합니다

2026-10-12 에 [문의하기](inquiry.md)·병원 상세 `문의` 섹션·[관리자 문의 화면](admin-inquiries.md)이 생겼습니다.
**서버에는 아직 문의 기능이 없어서** 상담·찜과 같은 방식(브라우저 저장)으로 먼저 만들었고, 그래서 남는 한계가 다음과 같습니다.

- **문의도 답변도 이 브라우저 안에만 저장됩니다.** 다른 컴퓨터·시크릿 창에서는 보이지 않고, 브라우저 데이터를 지우면 사라집니다. 실제로 병원에 전달되지도 않습니다
- **문의 샘플 데이터가 없습니다.** 모든 병원이 처음에는 `아직 공개된 문의가 없어요` 입니다. 샘플을 넣으려면 `frontend/src/mocks/fixtures/` 가 자연스러운 자리인데 **그 폴더는 백엔드 seed 가 그대로 import 하는 원본**이라, 서버에 없는 테이블의 가짜 행을 넣지 않았습니다
- **답변 알림에 받는 사람이 없습니다.** 알림이 `audience=user` 로만 저장되어, 같은 브라우저의 다른 계정으로 로그인해도 `문의에 답변이 왔어요` 가 보입니다 (위 🔴 "다른 사람의 알림이 보입니다" 와 같은 뿌리입니다). 알림을 눌러 열리는 `내 문의` 탭은 계정별로 갈려서 **질문 본문과 나머지 답변은 보이지 않지만**, 알림 줄 자체에 `{병원명} · 답변 앞 60자` 가 적혀 있어 **그 60자는 같은 브라우저의 다른 계정에게도 읽힙니다** (비공개로 답한 건도 마찬가지입니다). 알림에 받는 사람이 생겨야 닫힙니다
- **문의자 이름을 문의 행에 적어 둡니다.** 서버는 `users.name` 을 조인해 마스킹하고 이름 스냅샷을 두지 않기로 했는데(`docs/api/README.md` §4), 로컬에는 사용자 표가 없어 **작성 시점의 이름**을 저장합니다. 계정 이름을 바꿔도 관리자 화면에는 옛 이름의 마스킹(`김*준`)이 남습니다. 병원 이름도 같은 이유로 작성 시점 값입니다 (답변 알림 문구에 병원명이 필요합니다)
- **관리자 문의 목록은 100건까지만 보입니다.** 페이지 이동 UI 가 없어 계약 상한만큼 한 번에 받습니다. 탭의 숫자는 전체를 세므로, 101건을 넘으면 숫자가 목록보다 커집니다 (상담 목록·알림함과 같은 숙제입니다)
- **병원 상세의 공개 Q/A 도 20건까지만 받아옵니다.** `문의 더보기` 는 **받아온 목록을 펼칠 뿐** 다음 쪽을 더 불러오지 않습니다. 21번째부터는 `문의 N건 · 답변 N` 의 숫자에는 들어가지만 목록에는 나오지 않습니다
- **답변은 수정·삭제할 수 없고, 문의도 취소할 수 없습니다.** 일부러 그렇게 두었습니다 (답변이 조용히 바뀌면 `문의에 답변이 왔어요` 알림이 거짓이 됩니다). 신고·숨김 경로도 없습니다
- **도배를 막는 규칙이 없습니다.** 같은 사람이 같은 병원에 연속으로 문의할 수 있습니다. 서버의 요청 한도가 1차 방어선인데 서버가 아직 없습니다
- **관리자 문의 화면에 병원별 필터가 없습니다.** 담당 병원이 여러 곳이면 한 목록에 섞여 나오고, 목록 항목에 병원 이름이 보이지 않습니다 (계약에는 `hospitalId` 필터가 있습니다 — 화면만 아직 없습니다)
- **주제별 필터도 화면에 없습니다.** 계약에는 있습니다
- **인가가 진짜가 아닙니다.** "담당 병원만 보인다"·"운영자는 답변할 수 없다" 는 판정을 프론트의 api 계층이 흉내 낸 것이라, 브라우저 안에서 상태를 고치면 뚫립니다. 서버가 생겨야 닫히는 구멍이고, 상담·찜도 같은 상태입니다

### 인터넷이 끊기면 "불러오지 못했어요" 대신 "불러오는 중" 이 계속됩니다

기기가 **오프라인**이면 서버에 묻는 화면들이 실패를 알리지 않고 기다립니다. 검색 화면의 병원·원장님
추천은 회색 자리표시가 계속 남고 `다시 시도` 가 나오지 않으며, Enter 를 눌러도 `지금은 검색할 수
없어요` 대신 돌아가는 표시만 보입니다. 병원 탐색은 오히려 `조건에 맞는 병원이 없어요` 처럼
**결과가 없다고** 보입니다. 인터넷이 돌아오면 몇 초 안에 저절로 채워집니다. (서버만 안 될 때는
실패 안내가 정상으로 뜹니다 — QA 2026-10-13 확인)

> 개발자 메모: TanStack Query 의 기본 `networkMode: 'online'` 때문에 `navigator.onLine === false`
> 면 쿼리가 **일시정지**되어 요청도 오류도 생기지 않습니다(`frontend/src/app/providers.tsx`).
> `offlineFirst` 로 바꾸면 실패로 떨어지지만 앱 전체 동작이 바뀌므로 따로 정합니다.

### 지도가 보이지 않습니다

카카오맵 API 키가 설정되지 않아서 지도 자리에 `카카오맵 API 키가 설정되지 않았어요` 만 표시됩니다. 병원 탐색의 지도 보기, 병원 상세의 지도 창 모두 해당합니다.

### ~~시술 분야 세 곳은 광고 병원이 위로 안 올라가고 100곳까지만 보입니다~~ — 해결됨 (2026-10-21, 요청 14)

서버가 분야를 직접 알게 되어 병원 탐색 탭·시술 카테고리 `전체`·검색 추천이 모두 분야 하나로 한 번에
묻습니다. 그래서 `충치치료` `심미` `턱관절·스플린트` 를 포함한 **모든 분야에서 광고 병원(평점 3.5

## 🟡 관리자 화면 — 데이터가 잘못될 수 있는 것

### 병원 정보 수정에서 대표 이미지를 바꿔도 병원 상세 사진이 그대로입니다

병원 정보 **수정** 화면에서 대표 이미지 주소를 바꿔도 병원 상세 화면의 사진 캐러셀에는 반영되지
않습니다. 캐러셀(`Hospital.images`)과 대표 이미지(`Hospital.thumbnail`)가 서로 다른 필드이고,
수정 화면은 의도적으로 `images` 를 건드리지 않기 때문입니다 — 여러 장의 진짜 사진을 가진 병원의
갤러리를 대표 이미지 한 장으로 덮어쓰는 사고를 피하려는 것입니다. 캐러셀을 직접 편집하는 화면이
생기기 전까지 남는 한계입니다.

> **2026-08-14 갱신 — 신규 등록은 해결됐습니다.** 등록 화면은 이제 대표 이미지 값을
> `images: [thumbnail]` 로 캐러셀에도 함께 넣습니다(대표 이미지를 비워도 화면이 쓰는 플레이스홀더
> 이미지가 들어가 캐러셀이 비지 않습니다). 위 증상은 **수정** 화면에만 남아 있습니다.

### 인증된 전문의의 전문 분야를 바꿔도 재검수되지 않습니다 — 해결됨

승인된 전문의의 전문 분야를 다른 과로 바꾸면 인증 상태가 `대기` 로 되돌아가고, 새 과의 검수를 다시 받아야 배지가 노출됩니다.

### 전문의 승인/반려 결과가 병원에 통보되지 않습니다 — 절반만 해결됨

전문의 인증을 승인·반려하면 이제 서버가 그 병원 담당자 전원에게 알림 행을 만듭니다. 다만 **알림함
화면이 아직 그 알림을 읽어오지 않습니다** — 알림함은 여전히 예전 방식(브라우저 저장)을 쓰고
있어서, 병원 담당자에게는 지금도 검수 결과가 화면에 보이지 않습니다. 알림함이 서버 알림을 읽어오면
자동으로 완성됩니다.

### 같은 상태를 다시 눌러도 처리됩니다 — 해결됨

같은 값으로 다시 저장하면 **아무 일도 일어나지 않습니다.** 처리 이력도, 환자 알림도 늘지 않습니다.

> **2026-08-19 갱신 / 2026-10-13 확장.** `frontend/src/features/consult/api/consultApi.ts` 의
> `updateConsultStatus` 는 이제 `(상태, 확정 일시, 취소 사유)` **세 값**을 현재와 비교해
> 전부 같으면 저장도 알림도 하지 않습니다(no-op). 일시 비교는 **분 단위**라 초 자릿수 때문에
> 거짓 변경이 되지 않습니다. `consultApi.test.ts` 가 그 동작을 고정합니다.
>
> 같은 날 **목록의 빠른 상태 버튼 자체를 없앴고**(요청서 `2026-10-12-04`), 상태 변경은 상세에서
> 고른 뒤 `저장` 을 눌러야 일어납니다 — "확인창 없이 바로 바뀝니다" 도 함께 사라졌습니다.

### 상담 예약 화면의 한계 — 화면은 전부 동작합니다

2026-10-13 에 상담 화면이 [상담 예약](admin-consultations.md)으로 바뀌면서 **해결된 것들**:
모든 병원의 상담이 섞여 나오던 문제(이제 담당 병원만), 목록에 전체 번호가 그대로 보이던 문제
(이제 `010-****-4411`), 확인창 없이 바로 바뀌던 상태(이제 고른 뒤 `저장`), 예약 날짜를 적을 칸이
없어 메모에 적던 문제(이제 `확정 날짜`·`시간`). 남은 한계는 다음과 같습니다.

- **서버에 상담 기능이 아직 없습니다.** 목록·상세·상태 변경·메모 전부 **브라우저 안**(localStorage)에
  저장되고, 계약(`docs/api/openapi.yaml` 의 consult 절)을 프론트의 api 계층
  (`frontend/src/features/consult/api/consultApi.ts`)이 흉내 냅니다. 다른 컴퓨터에서는 다른 목록이 보입니다
- **인가가 진짜가 아닙니다.** "담당 병원만 보인다" · "운영자는 상태를 바꿀 수 없다" · "전체 번호는
  담당자 상세에만" 을 전부 프론트가 판정하므로, 브라우저 안에서 로그인 상태를 고치면 뚫립니다.
  서버가 생겨야 닫히는 구멍이고, 문의·찜도 같은 상태입니다
- **열람 기록(감사 로그)이 남지 않습니다.** 계약은 상세를 열 때마다 "누가 전체 번호를 봤는가" 를
  기록하게 되어 있지만(`X-Audit-Logged`), 로컬에는 그 테이블도 서버 시계도 없습니다
- **병원 이름을 상담과 함께 받지 못해 따로 조회합니다.** 계약(`ConsultRequest.hospitalName`)은 이름을
  함께 내려주지만 로컬 응답에는 없어서, 카드와 상세가 **병원 id 로 병원을 한 번 더 조회**합니다
  (`features/hospital/useHospitalName` — 마이페이지 상담 내역과 같은 훅). 같은 병원의 카드는 조회를
  공유하므로 목록 한 장에 **병원 수만큼** 요청이 나가고, 불러오는 동안 이름 자리에 `—` 가 보입니다.
  서버가 이름을 함께 내려주면 이 조회는 사라집니다
- **100건까지만 보입니다.** 페이지 이동 UI 가 없어 계약 상한(`pageSize` 100)만큼 한 번에 받습니다.
  탭 숫자는 전체를 세므로 101건을 넘으면 숫자가 목록보다 커집니다 (알림함·문의 목록과 같은 숙제)
- **`유입`(어느 화면에서 신청했는지)은 의도적으로 만들지 않았습니다.** 신청 화면이 그 값을 보내지
  않아 지금 만들면 **전 건이 빈칸**인 자리가 생깁니다. 필요해지면 상담 접수에 `source` 를 더하는
  것이 먼저이고, 그때도 과거 건은 영원히 알 수 없습니다 (요청서도 "데이터가 없으면 빼도 됩니다")
- **`엑셀로 내려받기` 도 의도적으로 만들지 않았습니다.** 그것은 명백한 대량 반출이라 열람 기록과
  권한 설계가 먼저입니다 (위 감사 로그 항목)
- **운영자는 상담을 처리할 수 없습니다.** 병원이 방치한 건을 운영자가 취소하는 요구가 있을 법하지만
  요청서에 없어 바꾸지 않았습니다 — 미결 사항입니다
- **취소 사유 `기타` 에 설명 칸이 없습니다.** 메모가 그 자리입니다. `기타` 비율이 높게 나오면
  설명 칸보다 **사유 코드를 늘리는 것이 먼저**입니다
- **메모에 작성자 표시가 없습니다.** 처리 이력에는 처리자 이름이 남지만 메모에는 아직 없습니다
- **계약 확장 이전에 `예약확정` 이 된 건에는 확정 일시가 없습니다.** 소급해 채우지 않았으므로
  (메모에 적힌 날짜를 파싱하는 것은 추측입니다) 화면이 `일시 미입력` 로 보여주고 담당자가 채웁니다

### 미승인 전공을 가진 전문의가 있는 병원에는 새 전문의를 추가할 수 없습니다

병원에 검수 대기 중이거나 반려된 전문의가 한 명이라도 있으면, 그 병원에 새 전문의를 추가하는 저장이
막힙니다. **화면(관리자 병원 폼)이 저장 버튼 자체를 비활성화해서 막는 것**이고, 요청이 서버까지
가지도 않습니다 — 관리자가 미승인 전공을 대신 지어내 보낼 방법이 없기 때문입니다(전문의 로스터를
통째로 교체하는 저장 방식이라 모든 항목에 전공이 필요합니다). 기존 전문의의 정보 수정·삭제는
영향받지 않습니다 — 새로 추가할 때만 막힙니다.

### 두 전문 분야는 전문의 등록 시 시술이 자동으로 채워지지 않습니다 — 절반만 해결됨 (2026-10-21, 요청 14)

- **`소아치과전문의` 는 해결됐습니다.** 시술이 31개로 늘면서 `불소도포`·`실란트` 가 소아치과의
  시술이 되어, 새로 등록하면 자동으로 붙습니다
- **`구강악안면방사선과전문의` 는 일부러 그대로 둡니다.** 영상 진단은 세부 시술 31개 어디에도
  해당하지 않아 자동으로 붙일 시술이 없고, 시술 목록이 **0건**인 것이 맞습니다
- **새로 생긴 주의점:** 2026-10-21 부터 자동 배정은 "그 전공의 시술 **중 그 병원이 취급하는 것만**"
  입니다. 그래서 어느 전공이든 병원이 그 전공의 시술을 하나도 등록하지 않았으면 **에러 없이 0건**이
  됩니다(예: `불소도포`·`실란트` 를 등록하지 않은 병원의 소아치과 전문의). 병원이 하지 않는 시술이
  전문의 프로필에 붙던 문제를 막으려고 고른 규칙입니다

관리자 화면에는 전문의의 담당 시술을 직접 고르는 칸이 없어서, 0건이 된 전문의는 지금 화면에서
고칠 방법이 없습니다. 병원의 취급 시술을 **먼저 저장한 뒤** 전문의를 추가해야 그 시술이 붙습니다
(자동 배정은 전문의를 추가하는 순간 서버에 저장돼 있는 병원 시술을 봅니다).

### 병원 등록 화면에서 넣은 전문의가 저장되지 않습니다

2026-10-21 문서 갱신 중 코드에서 발견했고, 같은 날 요청 14 QA 가 **실제 서버에서 확인했습니다**(병원 등록
요청에 전문의 1명을 실어 보내면 병원은 `201` 로 만들어지지만 그 병원의 전문의 목록은 0명). 병원 등록
화면은 병원과 전문의를 한 요청에 실어 보내지만(`frontend/src/pages/admin/AdminHospitalNewPage.tsx`,
`useCreateHospital.ts` 주석은 "한 요청으로 원자적으로 생성된다" 고 적고 있습니다), 계약의 병원 등록
요청(`HospitalCreateRequest`)과 서버의 입력 검사(`backend/src/hospital/hospital.schemas.ts` 의
`createHospitalSchema`)에는 전문의 칸이 없어 **서버가 그 부분을 조용히 버립니다.** 등록 뒤 병원 정보
수정의 `의료진` 에서 다시 넣으면 저장됩니다. 요청 14 와는 별개로 그 전부터 있던 동작이라 이번에 고치지
않았습니다 — 고치려면 계약에 등록 요청의 전문의 칸을 넣을지(서버가 한 번에 저장), 화면이 등록 후 두 번째
요청으로 보낼지 먼저 정해야 합니다.

### 대시보드의 `오늘`·`이번 달` 숫자가 샘플만으로는 0입니다

샘플 상담 데이터의 날짜가 2026년 6~7월이라 현재 월과 맞지 않습니다. 그래서 대시보드의
`오늘 들어온 상담` · `이번 달 예약확정` · `이번 달 상담 흐름` 과 `오늘 내원 예정` 은
**직접 한 건 신청해 봐야** 숫자가 보입니다. 같은 이유로 상담 예약
화면의 **`오늘`·`이번 주` 필터와 `지연` 배지도 샘플만으로는 재현되지 않습니다** — 직접 한 건
신청해야 보입니다. **기본 기간이 `최근 30일` 이라 상담 예약 화면을 처음 열면 샘플 7건도 보이지
않습니다**(빈 화면이 `최근 30일 기준이에요…` 라고 알려 주고, `전체 기간 보기` 를 누르면 보입니다) (시드 파일 `frontend/src/mocks/fixtures/consultRequests.ts` 는 백엔드 seed 가
그대로 import 하는 파일이라 이 작업에서 건드리지 않았습니다).

### 관리자 홈의 상담 숫자 카드는 담당 병원으로 나뉘지 않습니다 — 해결됨

2026-10-13 에 `/admin` 이 대시보드로 바뀌면서 닫혔습니다. 모든 숫자가 **메뉴에서 고른 담당 병원
한 곳** 기준이고, 사이드 배지와 카드가 **한 응답**(`GET /admin/dashboard?hospitalId=`)에서 와서
서로 어긋날 수 없습니다. 담당 병원이 2곳 이상이면 메뉴 위 드롭다운에서 고릅니다.

(옛 숫자의 출처였던 `GET /consult-requests/summary` 는 계약에만 남아 있고 **지금은 어느 화면도 부르지 않습니다** —
그쪽은 담당 병원 전체 합산이고 `pending` 의 뜻도 다릅니다. `docs/api/README.md` §14.)

### 관리자 대시보드의 집계가 브라우저 안에서 계산됩니다

`GET /admin/dashboard` 는 **계약만 있고 서버 구현이 없습니다**(세는 대상인 상담·문의 모듈도
없습니다). 그래서 프론트의 api 계층(`frontend/src/features/admin/api/dashboardApi.ts`)이 같은
응답 모양을 흉내 냅니다 — 상담·문의는 브라우저 저장소에서, 병원과 소속 전문의는 **진짜 서버**에서
읽습니다. 그 결과:

- **숫자는 이 브라우저 기준입니다.** 다른 컴퓨터·시크릿 창에서는 다른 숫자가 보입니다
- **한 트랜잭션이 아닙니다.** 상담·문의와 병원·전문의가 서로 다른 곳에서 오므로 엄밀히는
  한 시점이 아닙니다. 대신 시계를 **함수 진입 때 한 번만** 읽어 달력 경계(`오늘`·`이번 달`)와
  지연 판정이 같은 시점을 쓰게 합니다
- **인가가 진짜가 아닙니다.** 운영자 차단(`403 OPERATOR_CANNOT_USE_DASHBOARD`)·담당 병원 밖
  차단(`403 HOSPITAL_NOT_MANAGED`)을 전부 프론트가 판정합니다 (상담·문의와 같은 한계)
- **담당 병원이 0곳인데 `hospitalId` 를 생략한 경우를 계약이 적지 않았습니다.** 로컬 구현은
  `422 HOSPITAL_ID_REQUIRED` 로 떨어뜨리고, 화면은 그 상태에서 아예 호출하지 않습니다

### 관리자 대시보드에서 아직 만들지 않은 것

전부 **근거가 있어 미룬 것**입니다 (`docs/database/README.md` §13.10).

- **자격증 반려 사유가 보이지 않습니다.** 반려된 전문의의 **이름까지만** 보여줍니다 — 사유
  (`rejectionReason`)는 관리자 시야로 소속 전문의를 읽는 서버 기능이 아직 없습니다
  (`GET /hospitals/{id}/doctors?view=admin` 후보)
- **`지연` 만 모아 보는 필터가 없습니다.** 상태도 기간도 아닌 세 번째 필터 축이 탭 옆에 생깁니다.
  지연 건은 `오늘 할 일` 에 건별로 나열되고 거기서 상세로 갑니다
- **`오늘 내원 예정` 에 `전체 보기` 가 없습니다.** 날짜별 내원 목록 화면이 없어서 그 목록을
  재현하는 조건(`visitDate`)도 만들지 않았습니다
- **완성도 항목 둘이 빠져 있습니다** — `시술별 가격` 과 `병원 사진 3장 이상`. 둘 다 **오늘
  채울 수단이 없어서**(가격 칸·파일 업로드가 없습니다) 입력 칸이 생기는 **요청 07** 의 자리입니다
- **메뉴 아래에 담당자 직책과 승인 상태(`승인 완료 · 앱 노출 중`)가 없습니다.** 저장되는 곳이
  없어 **요청 06** 과 함께 설계합니다. 지금은 병원명과 이름만 보여줍니다
- **깔때기의 `연락 완료` 막대만 상담 목록으로 정확히 열 수 없습니다.** 취소 사유가 조건에
  걸려 있어 상태 탭으로 표현되지 않습니다

### 고른 담당 병원이 브라우저에 남습니다

관리자 메뉴에서 고른 병원은 이 브라우저에 기억됩니다(`mola.admin.hospitalId`). **계정이 바뀌면
지우고**, 읽을 때마다 담당 병원 목록으로 검증해 범위 밖이면 버리므로 남의 병원이 열리지는
않습니다. 다만 상담·문의 저장소와 마찬가지로 **기기마다 다른 값**입니다 — 서버는 이 선택을
기억하지 않습니다(기기마다 달라도 되는 값이라는 판단입니다).

### `/explore?category=<옛 시술 id>` 는 분야 전체로 넓어집니다

북마크해 둔 `/explore?category=crown` 같은 옛 주소로 들어오면 그 시술이 속한 **분야**

2026-10-21(요청 14) 이후에도 그대로입니다. 그날 이름이 바뀐 옛 시술 주소(`?category=gum-disease`,

`?sub=` 에 옛 이름이 와도 지금 이름의 세부 시술(`잇몸치료`)이 골라진 채로 열립니다.
