# 0001 — 역할 구조와 개인정보 열람 범위

**날짜**: 2026-08-12
**상태**: 확정 — **결정 2 는 2026-10-21 개정**(직접 가입 + 승인 대기), **결정 3 은 2026-10-21 확정**
**개정**: 2026-10-21 — 협업자가 떠나 혼자 개발 체제가 되면서(요청서 12) 제안으로 남아 있던 것을 결정으로 바꿨다. 예전 문장은 지우지 않고 "기록" 으로 남겼다
**영향**: DB 스키마, API 인가, `/admin` 화면 구조

---

## 배경

전문의 인증 검수 화면(`/admin/specialists`)이 **모든 병원의 전문의**를 심사하는 구조인데, 초기 API 설계는 역할을 `user` / `admin`(병원 관리자) 둘로 잡았다. 그러면 병원 관리자가 남의 병원 전문의를 심사하게 된다. DB 설계는 이 필요를 발견해 `operator` 를 추가했고, 두 산출물이 어긋난 상태였다.

또한 지금 관리자 화면에는 인가가 전혀 없어서, 주소만 알면 누구나 고객 실명·전화번호를 볼 수 있다 (`docs/features/known-issues.md`).

## 결정 1 — 역할 3개 (사용자 결정)

| 역할 | 하는 일 |
|---|---|
| `user` | 일반 사용자. 병원 탐색, 상담 신청, 찜, 커뮤니티 |
| `hospital_admin` | 병원 담당자. **자기 병원**의 정보·전문의·상담만 다룬다 |
| `operator` | 플랫폼 운영자. 전문의 인증 검수, 병원 생성, 담당자 지정 |

`hospital_admins(user_id, hospital_id)` M:N 으로 담당 범위를 정한다. 한 사람이 여러 병원을 담당할 수 있다.

**화면 구조가 갈라진다:**

- `/admin` — 담당자는 자기 병원만, 운영자는 전체 목록
- `/admin/specialists` — **운영자 전용.** 담당자는 접근 불가
- `/admin/hospital/new` — **운영자 전용**
- `/admin/hospital/:id` — 담당 병원만 (운영자는 전체)
- `/admin/consultations*` — 담당 병원에 들어온 상담만

## 결정 2 — 병원 관리자는 직접 가입하고, 승인 전에는 환자 앱에 노출되지 않는다 (2026-10-21 개정)

> **개정 이력**: 2026-08-12 처음 결정은 "병원 관리자 계정은 운영자가 만든다 (기본값, 미확답)" 였다 —
> 아래 [개정 전 결정 2](#개정-전-결정-2-2026-08-12--기록) 에 그대로 남겼다. 2026-10-13 요청서 06 에서
> 요청자가 아래 4가지를 확정했고 변경 제안을 붙였지만, 그때는 서버가 협업자 영역이라 "협업자 확인 대기" 로
> 두었다. 2026-10-21 협업자가 떠나 확인할 사람이 없어졌고(요청서 12), 요청자가 이미 확정한 내용이므로
> **그 제안을 결정으로 채택했다.** 구현은 **요청서 18** (구 06) 이 한다 — 열린 질문의 답도 그 요청서에 있다.

**요청자가 확정한 것 (2026-10-13)**

1. **직접 가입 + 승인 대기**로 간다. **초대 코드가 아니다**
2. 개발 단계에서는 **자동 승인**. 운영자 검수 화면은 별도 작업(단 데이터는 그것을 받친다)
3. 승인 전: **관리자 화면은 쓴다. 환자 앱에는 병원이 노출되지 않는다**
4. 사업자등록증의 저장·열람 권한은 **운영자만**

```
병원 담당자가 회원가입에서 `치과 관계자이신가요?` 토글을 켠다
  → 한 트랜잭션: users(role=hospital_admin) + hospitals(approval_status=pending)
                 + hospital_admins(+직책) + 사업자등록증 파일 + 약관 동의 4종
  → 관리자 화면은 즉시 쓴다. 환자 앱에는 보이지 않는다 (isPubliclyListed)
  → 운영자가 사업자등록증을 검수해 승인/반려  (개발 단계에서는 자동 승인)
  → 승인된 순간 환자 앱에 나타난다
```

- 운영자 경로(`POST /hospitals` + `POST /hospitals/{id}/admins`)는 **그대로 남는다.** 없어지는 것은
  "유일한 경로" 라는 말뿐이다 (대량 이관·대행 등록이 여전히 그 경로다)
- 입점 문의(`partner_inquiries`)도 **그대로 남는다.** 가입 의사가 없는 사람의 입구다.
  직접 가입은 `partner_inquiries` 행을 만들지 않는다
- **`operator` 를 담당자로 지정할 수 없다**(`422 CANNOT_ASSIGN_OPERATOR`)는 그대로다.
  같은 이유로 **`operator` 계정은 이 가입 경로로 병원을 만들 수 없다** — 역할 분리가 무너진다
- 승인 취소(강제 비노출)는 `approval_status` 되돌리기가 아니라 `deleted_at` 이다

**왜 바꿨나**: 처음 결정이 걱정한 "아무나 병원을 만들 수 있다" 는 여전히 옳은 걱정이다. 개정은 그것을
**생성 금지**가 아니라 **노출 금지**로 막는다 — 지키려던 것은 "검증 없이 _노출_ 되면 안 된다" 였다.
운영 쪽 이유는 입점 병원을 늘리는 단계에서 운영자가 계정을 일일이 만들면 병목이 된다는 것이다.
자세한 근거·기각한 대안(초대 코드)은 아래 [변경 제안](#변경-제안-2026-10-13--2026-10-21-채택) 에 있다.

### 개정 전 결정 2 (2026-08-12) — 기록

> 2026-10-21 까지 유효했던 처음 결정이다. 지우지 않고 남긴다.

**병원 관리자 계정은 운영자가 만든다 (기본값, 미확답)**

사용자 답변을 받지 못해 **가장 안전한 쪽**으로 정했다. 되돌리기 쉬운 결정이다.

```
병원이 `병원 입점 문의` 제출
  → 운영자가 심사
  → 운영자가 병원 생성 + 담당자 계정 지정(또는 기존 계정 승격)
```

**이 방식을 고른 이유:** 나머지 선택지는 전부 "아무나 병원을 만들 수 있다"로 귀결된다. 병원 정보는 환자가 시술을 결정하는 근거이므로 검증 없이 생성되면 안 된다. 자가 가입 + 승인 대기 방식은 승인 전 상태의 화면을 따로 만들어야 해서 지금 단계에서 비용이 더 크다.

지금 `준비중입니다` 한 줄뿐인 입점 문의 화면이 이 흐름의 시작점이 된다.

**바꾸고 싶으면:** 초대 코드 방식은 `hospital_admins` 에 `invite_code` 컬럼과 가입 엔드포인트 하나가 추가된다. 스키마 파괴 없이 가능하다.

**사용자가 확정한 것 (2026-10-13)**

#### 무엇이 왜 바뀌나

| | 결정 2 (지금) | 제안 |
|---|---|---|
| 병원 행을 만드는 사람 | **운영자만** (`POST /hospitals`) | 운영자 **또는** 가입하는 병원 본인 |
| 담당자 role 승격 | 운영자가 `POST /hospitals/{id}/admins` | 위 + 가입 트랜잭션이 직접 |
| 검증 시점 | **생성 전** (운영자가 심사하고 만든다) | **생성 후** (만들어지되 승인 전에는 환자에게 보이지 않는다) |
| 입점 문의 | 병원 생성의 **유일한** 시작점 | 입구 하나로 **공존**. 대체되지 않는다 |

**바꾸는 이유**는 결정 2 가 기각 근거로 든 것과 다른 축이다. 결정 2 는 **"아무나 병원을 만들 수 있다"**
를 피하려 했고 그 우려는 여전히 옳다. 제안은 그 우려를 **생성 금지**가 아니라 **노출 금지**로 막는다 —
병원 정보가 환자의 판단 근거라는 전제는 그대로 두되, 검증받지 않은 행이 환자에게 **도달하지 않으면**
그 전제는 깨지지 않는다. 바뀌는 것은 "검증 없이 생성되면 안 된다" 가 아니라
**"검증 없이 _노출_ 되면 안 된다"** 이고, 후자가 실제로 지키려던 것이다.

사용자가 든 이유는 운영 쪽이다: 입점 병원을 늘리는 단계라 **운영자가 계정을 일일이 만들면 병목**이 된다.

#### "승인 전 화면을 따로 만들어야 해서 비용이 크다" 에 대한 답

결정 2 가 자가 가입을 기각한 **유일한 비용 근거**였다. 그 비용이 두 가지 이유로 사라졌다.

1. **승인 전용 화면을 만들지 않는다.** 승인 대기 병원이 보는 관리자 화면은 **승인된 병원이 보는 화면과
   같은 화면**이다. 상담·문의가 0건이고 숫자 카드가 전부 0 일 뿐이며, 그 상태는 **오늘도 정상 상태**다
   (방금 등록된 병원이 그렇다). 새로 만드는 UI 는 사이드 메뉴 하단의 **상태 배지 한 줄**
   (`승인 완료 · 앱 노출 중` / `승인 대기`)과 가입 완료 안내뿐이다 —
   그 배지는 이미 요청 05 에서 자리가 잡혀 있고 **저장될 곳이 없어서 미뤄져 있었다**
   (`docs/features/known-issues.md`, `docs/database/README.md` §13.10-5)
2. **그 사이 `/admin` 이 실제로 만들어졌다.** 결정 2 를 쓴 2026-08-12 에는 인가조차 없었다.
   지금은 역할 3개·담당 범위·대시보드·상담·문의 화면이 있고, **승인 대기 병원이 쓸 화면이 이미 전부 있다.**
   "따로 만들어야 하는 화면" 의 목록이 그때와 다르다

대신 **새로 생기는 비용**은 화면이 아니라 **질의**다. 지금까지 `hospitals` 에 행이 있다는 것은 곧
환자가 볼 수 있다는 뜻이었는데(`deleted_at IS NULL` 하나), 그 등식이 깨진다. 노출 판정을 빠뜨린 질의
한 곳이 곧 "승인 안 난 병원이 앱에 떴다" 는 사고다. 그래서 판정을 **순수 함수 하나**
(`isPubliclyListed`)로 두고 그것이 걸리는 자리를 전부 열거했다 (`docs/database/README.md` §14.4).

#### 대안 "초대 코드" 를 기각한 이유

결정 2 가 "스키마 파괴 없이 가능" 하다고 적어 둔 대안이다. 기술 비용은 실제로 가장 싸다. 기각한 이유:

- **병목이 그대로다.** 코드를 발급하는 사람이 운영자다. 해결하려던 문제(운영자가 일일이 처리)가
  "계정 만들기" 에서 "코드 발급하기" 로 이름만 바뀐다
- **코드를 전달할 수단이 없다.** 이메일 발송 인프라가 없다(결정 4·§3 이 초기 비밀번호 전달을 포기한
  것과 같은 사정). 전화로 불러 주는 코드는 전달 과정에서 새고, 샌 코드는 **검증 없는 병원 생성**이 된다
- **코드는 병원을 검증하지 않는다.** 사업자등록증을 받는 흐름이 따로 필요한데, 그러면
  초대 코드 + 서류 검수 **두 관문**이 되어 직접 가입보다 복잡해진다
- **가입 문턱을 낮춘다는 요청의 목적과 정반대다.** 병원이 먼저 연락해야 코드를 받는다

사람이 없다. 우선순위가 한 번 더 올라갔다).

## 결정 3 — 고객 실명·전화번호는 담당 병원만 (2026-10-21 확정)

> **개정 이력**: 2026-08-12 에는 사용자 답을 받지 못해 "기본값, 미확답" 으로 정했다. 그 뒤 이 결정대로
> 관리자 상담 화면(요청서 04 — 목록 연락처 가림, 운영자 마스킹, 상세 열람 기록)이 만들어졌고,
> 2026-10-21 요청자가 **확정**했다(요청서 12). 아래 본문은 그대로다.

| 보는 사람 | 상담 신청자 이름 | 연락처 |
|---|---|---|
| `hospital_admin` (담당 병원) | 전체 | 전체 |
| `operator` | `박*영` | `010-****-5678` |
| 그 외 | 접근 불가 | 접근 불가 |

**이 방식을 고른 이유:** 연락해야 하는 사람만 보면 된다. 운영자는 분쟁·CS 확인을 위해 상담의 존재와 상태·이력은 봐야 하지만, 연락처 자체가 필요한 경우는 드물다. 마스킹은 서비스 계층의 투영(projection) 하나로 처리되므로 나중에 푸는 것도 한 줄이다.

**감사 로그는 이 결정에 따라오는 항목이다.** 담당 병원 관리자가 상담 상세를 열람한 기록을 남긴다 — 마스킹으로 운영자 쪽을 막았으므로 남는 노출면은 담당자 쪽이다.

**바꾸고 싶으면:** 운영자에게 전체를 보이려면 마스킹 투영을 끄면 된다. 그 경우 열람 로그를 필수로 남겨야 한다.

## 결정 4 — 첫 `operator` 는 API 로 만들지 않는다

API 설계 과정에서 드러난 문제: 모든 운영자 행위가 운영자 인증을 요구하는데 **첫 운영자를 만들 경로가 없다.** 병원 생성도 담당자 지정도 운영자만 할 수 있으므로, 운영자가 없으면 시스템이 아무것도 못 한다.

**운영자 승격은 HTTP 요청으로 불가능하게 둔다.** 그런 엔드포인트가 존재하면 그것이 시스템의 최고 권한 상승 표면이 된다 — 인증·인가에 어떤 결함이 생기든 그 경로 하나로 전권을 얻는다.

| 환경 | 방법 |
|---|---|
| 개발 | 시드 스크립트가 `operator` 계정을 만든다. `.env.example` 과 `backend/README` 에 자격증명을 기록 |
| 운영 | 서버 접근 권한이 필요한 CLI. `npm run operator:grant -- <email>` — DB 에 직접 쓰고 감사 로그를 남긴다 |

즉 **운영자 승격에는 파일시스템·DB 접근 권한이 필요하다.** 네트워크만으로는 도달할 수 없다.

`POST /hospitals/{id}/admins` 가 `operator` 계정을 담당자로 지정하는 것을 `422` 로 막는 것도 같은 이유다 (API 설계에서 추가됨) — 겸직하면 자기 병원 전문의를 스스로 검수할 수 있어 역할 분리가 무너진다.

## 미결로 남긴 것

이 결정에서 파생됐지만 지금 정하지 않아도 진행되는 것들.

1. **운영자 콘솔 화면** — 새 엔드포인트 6개(입점 문의 심사, 담당자 지정/해제)에 대응하는 화면이 없다. `/admin` 안에서 역할별로 숨길지 `/operator` 를 따로 만들지. `docs/features/` 에 화면 문서 추가가 필요하다
2. **`notifications.audience` 와 `users.role` 의 이름 겹침** — `audience` 값이 `[user, admin]` 인데 `role` 은 `[user, hospital_admin, operator]` 다. `audience=admin` 은 "병원 담당자용" 을 뜻하고 `operator` 의 관리자 알림함은 **비어 있는 것이 정상**이다(고객 이름이 박힌 알림을 마스킹 대상에게 보내지 않기 위해). 이름을 `[user, hospital]` 로 바꾸는 것이 맞지만 스키마·API·fixture 를 함께 고쳐야 하므로 알림 도메인 절단 시점에 처리한다
3. **`operator` 가 상담 상태를 못 바꾸는 것** — 병원이 응답하지 않는 상담을 운영자가 정리해야 하는 CS 상황이 생길 수 있다. 지금은 조회만 허용
4. **감사 로그 쓰기 실패 시 열람 허용 여부** — 트랜잭션으로 묶으면 로그 저장소 장애가 화면 장애가 되고, 안 묶으면 로그 없이 개인정보가 열람된다
5. **감사 로그 보존 기간** — 상담 데이터 보존 기간과 어긋나면 "이미 지운 상담을 누가 봤다" 기록만 남는다
6. **비밀번호 찾기의 우선순위가 올라갔다** — 계정을 운영자가 만들지 않는 설계이므로, 담당자가 비밀번호를 잊으면 병원 관리가 막히고 대신 재설정해 줄 수단이 없다 → **요청서 20** 에서 다룬다
7. **담당자 지정·해제를 당사자에게 통보할지** — 전문의 검수 결과는 통보하는데 권한 부여는 안 하는 것이 일관성이 없다. 특히 해제는 갑자기 관리자 화면이 사라지는 일이다
