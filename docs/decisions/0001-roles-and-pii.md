# 0001 — 역할 구조와 개인정보 열람 범위

**날짜**: 2026-08-12
**상태**: 확정
**영향**: DB 스키마, API 인가, `/admin` 화면 구조

---

## 배경

전문의 인증 검수 화면(`/admin/specialists`)이 **모든 병원의 전문의**를 심사하는 구조인데, 초기 API 설계는 역할을 `user` / `admin`(병원 관리자) 둘로 잡았다. 그러면 병원 관리자가 남의 병원 전문의를 심사하게 된다. DB 설계는 이 필요를 발견해 `operator` 를 추가했고, 두 산출물이 어긋난 상태였다.

또한 지금 관리자 화면에는 인가가 전혀 없어서, 주소만 알면 누구나 고객 실명·전화번호를 볼 수 있다 (`docs/features/known-issues.md`).

---

## 결정 1 — 역할 3개 (사용자 결정)

| 역할 | 하는 일 |
|---|---|
| `user` | 일반 사용자. 병원 탐색, 상담 신청, 찜, 커뮤니티 |
| `hospital_admin` | 병원 담당자. **자기 병원**의 정보·전문의·상담만 다룬다 |
| `operator` | 플랫폼 운영자. 전문의 인증 검수, 병원 생성, 담당자 지정 |

`hospital_admins(user_id, hospital_id)` M:N 으로 담당 범위를 정한다. 한 사람이 여러 병원을 담당할 수 있다.

**화면 구조가 갈라진다:**

- `/admin` — 담당자는 자기 병원만, 운영자는 전체 목록
- `/admin/specialists` — **운영자 전용.** 담당자는 접근 불가
- `/admin/hospital/new` — **운영자 전용**
- `/admin/hospital/:id` — 담당 병원만 (운영자는 전체)
- `/admin/consultations*` — 담당 병원에 들어온 상담만

---

## 결정 2 — 병원 관리자 계정은 운영자가 만든다 (기본값, 미확답)

사용자 답변을 받지 못해 **가장 안전한 쪽**으로 정했다. 되돌리기 쉬운 결정이다.

```
병원이 `병원 입점 문의` 제출
  → 운영자가 심사
  → 운영자가 병원 생성 + 담당자 계정 지정(또는 기존 계정 승격)
```

**이 방식을 고른 이유:** 나머지 선택지는 전부 "아무나 병원을 만들 수 있다"로 귀결된다. 병원 정보는 환자가 시술을 결정하는 근거이므로 검증 없이 생성되면 안 된다. 자가 가입 + 승인 대기 방식은 승인 전 상태의 화면을 따로 만들어야 해서 지금 단계에서 비용이 더 크다.

지금 `준비중입니다` 한 줄뿐인 입점 문의 화면이 이 흐름의 시작점이 된다.

**바꾸고 싶으면:** 초대 코드 방식은 `hospital_admins` 에 `invite_code` 컬럼과 가입 엔드포인트 하나가 추가된다. 스키마 파괴 없이 가능하다.

---

## 결정 3 — 고객 실명·전화번호는 담당 병원만 (기본값, 미확답)

| 보는 사람 | 상담 신청자 이름 | 연락처 |
|---|---|---|
| `hospital_admin` (담당 병원) | 전체 | 전체 |
| `operator` | `박*영` | `010-****-5678` |
| 그 외 | 접근 불가 | 접근 불가 |

**이 방식을 고른 이유:** 연락해야 하는 사람만 보면 된다. 운영자는 분쟁·CS 확인을 위해 상담의 존재와 상태·이력은 봐야 하지만, 연락처 자체가 필요한 경우는 드물다. 마스킹은 서비스 계층의 투영(projection) 하나로 처리되므로 나중에 푸는 것도 한 줄이다.

**감사 로그는 이 결정에 따라오는 항목이다.** 담당 병원 관리자가 상담 상세를 열람한 기록을 남긴다 — 마스킹으로 운영자 쪽을 막았으므로 남는 노출면은 담당자 쪽이다.

**바꾸고 싶으면:** 운영자에게 전체를 보이려면 마스킹 투영을 끄면 된다. 그 경우 열람 로그를 필수로 남겨야 한다.

## 결정 4 — 첫 `operator` 는 API 로 만들지 않는다

API 설계 과정에서 드러난 문제: 모든 운영자 행위가 운영자 인증을 요구하는데 **첫 운영자를 만들 경로가 없다.** 병원 생성도 담당자 지정도 운영자만 할 수 있으므로, 운영자가 없으면 시스템이 아무것도 못 한다.

**운영자 승격은 HTTP 요청으로 불가능하게 둔다.** 그런 엔드포인트가 존재하면 그것이 시스템의 최고 권한 상승 표면이 된다 — 인증·인가에 어떤 결함이 생기든 그 경로 하나로 전권을 얻는다.

| 환경 | 방법 |
|---|---|
| 개발 | 시드 스크립트가 `operator` 계정을 만든다. `.env.example` 과 `backend/README` 에 자격증명을 기록 |
| 운영 | 서버 접근 권한이 필요한 CLI. `npm run operator:grant -- <email>` — DB 에 직접 쓰고 감사 로그를 남긴다 |

즉 **운영자 승격에는 파일시스템·DB 접근 권한이 필요하다.** 네트워크만으로는 도달할 수 없다.

`POST /hospitals/{id}/admins` 가 `operator` 계정을 담당자로 지정하는 것을 `422` 로 막는 것도 같은 이유다 (API 설계에서 추가됨) — 겸직하면 자기 병원 전문의를 스스로 검수할 수 있어 역할 분리가 무너진다.

## 미결로 남긴 것

이 결정에서 파생됐지만 지금 정하지 않아도 진행되는 것들.

1. **운영자 콘솔 화면** — 새 엔드포인트 6개(입점 문의 심사, 담당자 지정/해제)에 대응하는 화면이 없다. `/admin` 안에서 역할별로 숨길지 `/operator` 를 따로 만들지. `docs/features/` 에 화면 문서 추가가 필요하다
2. **`notifications.audience` 와 `users.role` 의 이름 겹침** — `audience` 값이 `[user, admin]` 인데 `role` 은 `[user, hospital_admin, operator]` 다. `audience=admin` 은 "병원 담당자용" 을 뜻하고 `operator` 의 관리자 알림함은 **비어 있는 것이 정상**이다(고객 이름이 박힌 알림을 마스킹 대상에게 보내지 않기 위해). 이름을 `[user, hospital]` 로 바꾸는 것이 맞지만 스키마·API·fixture 를 함께 고쳐야 하므로 알림 도메인 절단 시점에 처리한다
3. **`operator` 가 상담 상태를 못 바꾸는 것** — 병원이 응답하지 않는 상담을 운영자가 정리해야 하는 CS 상황이 생길 수 있다. 지금은 조회만 허용
4. **감사 로그 쓰기 실패 시 열람 허용 여부** — 트랜잭션으로 묶으면 로그 저장소 장애가 화면 장애가 되고, 안 묶으면 로그 없이 개인정보가 열람된다
5. **감사 로그 보존 기간** — 상담 데이터 보존 기간과 어긋나면 "이미 지운 상담을 누가 봤다" 기록만 남는다
6. **비밀번호 찾기의 우선순위가 올라갔다** — 계정을 운영자가 만들지 않는 설계이므로, 담당자가 비밀번호를 잊으면 병원 관리가 막히고 대신 재설정해 줄 수단이 없다
7. **담당자 지정·해제를 당사자에게 통보할지** — 전문의 검수 결과는 통보하는데 권한 부여는 안 하는 것이 일관성이 없다. 특히 해제는 갑자기 관리자 화면이 사라지는 일이다

## 파급

- `docs/api/openapi.yaml` — `role` enum 을 `[user, admin]` → `[user, hospital_admin, operator]` 로. 검수 엔드포인트를 운영자 전용으로. 상담 응답에 마스킹 투영 추가. 임시로 넣었던 `403 SELF_VERIFICATION_FORBIDDEN` 은 불필요해지므로 제거
- `docs/database/schema.dbml`, `backend/prisma/schema.prisma` — 이미 3개 역할로 설계되어 있어 변경 없음
- `docs/features/*.md` — 관리자 화면 7개 문서의 "누가 보나요" 와 인가 경고를 실제 구현 후 갱신
- 감사 로그 테이블이 필요해진다 (DB 설계에서 "제안"으로 분리해 뒀던 `audit_logs`)
