비개발자가 낸 화면 기능 요청을 처리한다. 요청 내용: $ARGUMENTS

## 0. 요청을 확보한다

`$ARGUMENTS` 가 있으면 그것이 요청이다. 비어 있으면 `docs/features/requests/` 에서 `_TEMPLATE.md` 가 아닌 파일 중 **검토 결과의 상태가 `접수` 또는 `검토중`** 인 것을 찾는다. 여러 개면 목록을 보여주고 어느 것부터 할지 물어본다. 하나도 없으면 그 사실을 알리고 멈춘다.

## 1. 대상 화면을 특정한다

`docs/features/README.md` 의 화면 목록에서 요청이 가리키는 화면을 찾아 **해당 화면 문서를 읽는다.**

- 어느 화면인지 불분명하면 **추측하지 말고 물어본다.** 후보를 2~4개 제시한다.
- 여러 화면에 걸친 요청이면 전부 나열하고, 어디까지가 이번 범위인지 확인한다.

## 2. 이미 있는 기능인지 먼저 확인한다

**이 단계를 건너뛰지 않는다.** 비개발자는 기능이 이미 있는데 못 찾았을 수 있고, 있는 기능이 샘플 데이터라서 "안 된다"고 느꼈을 수 있다.

화면 문서의 기능 표와 실제 코드를 확인해서 다음 중 어느 경우인지 판정한다:

| 판정 | 대응 |
|---|---|
| 이미 있고 동작함 (✅) | 어디에 있는지 알려주고, 그래도 부족한 점이 있는지 되묻는다. 구현하지 않는다 |
| 있지만 샘플 데이터 (🟡) | "기능은 있고 데이터가 가짜"임을 설명한다. 요청이 데이터에 관한 것인지 기능에 관한 것인지 확인한다 |
| 껍데기만 있음 (🚧) | 실제로 만드는 작업이다. 계속 진행한다 |
| 아예 없음 | 새로 만드는 작업이다. 계속 진행한다 |

## 3. 요청을 개발 언어로 번역해서 확인받는다

비개발자의 문장을 그대로 구현하면 어긋난다. 다음을 정리해 **사용자에게 확인받고 진행한다**:

- 바뀌는 화면과 파일
- 새로 필요한 데이터가 있는지 (있으면 서버가 없는 지금 어디까지 가능한지)
- 이 요청이 다른 화면에 미치는 영향 — 화면 문서의 "함께 확인해야 하는 것" 절을 근거로
- **지금 스택에서 불가능하거나 큰 작업인 부분** — 있으면 솔직히 말하고 대안을 제시한다

요청자가 놓친 결정 사항이 있으면 여기서 묻는다. 예: 필터를 추가한다면 기본값이 켜짐인지 꺼짐인지.

## 4. 진행 중인 리팩터링과 충돌하는지 본다

`docs/superpowers/plans/` 의 계획서를 확인한다. 대상 화면이 아직 이관되지 않은 `frontend/src/screens/` 에 있고 곧 이관될 예정이면, **지금 고칠지 이관 후에 고칠지** 판단해서 알린다. 지금 고치면 이관 때 다시 손대야 한다.

## 5. 워크플로를 따른다

`CLAUDE.md` 의 개발 워크플로 규칙을 지킨다. 에이전트 이름은 현재 존재하는 것으로 매핑한다:

1. **새 화면이나 새 UI 요소가 생기면** → `designer` 에이전트로 설계를 먼저 받는다. 기존 요소의 문구·값만 바꾸는 것이면 생략한다
2. **구현** → `frontend-engineer` 에이전트. 테스트를 먼저 쓰게 한다
3. **리뷰** → `code-reviewer` 에이전트
4. **QA** → `qa-master` 에이전트. **QA 통과 전에는 완료라고 말하지 않는다**

에이전트에게는 반드시 알려준다:
- Node 가 PATH 에 없다. Git Bash 에서 `export PATH="$PATH:/c/Program Files/nodejs"`
- 완료 게이트: `npm run lint && npm run typecheck && npm run test:run && npm run build`, lint 는 0 errors

## 6. 화면 문서를 갱신한다

구현이 끝나면 **해당 화면 문서의 기능 표와 "알아두실 것"을 실제 상태에 맞게 고친다.** 이걸 빠뜨리면 문서가 거짓이 되고, 비개발자는 그걸 확인할 방법이 없다.

## 7. 요청서를 닫는다

요청서 파일이 있었으면 "검토 결과" 절을 채운다 — 상태, 영향 범위, 판단. 요청서가 없었으면(인라인 요청) 무엇을 했는지 요약만 남긴다.

## 8. 요청자에게 보고한다

**개발 용어를 쓰지 않는다.** 다음을 알린다:

- 무엇이 바뀌었는지 (사용자가 화면에서 보게 될 것)
- 어디서 확인할 수 있는지 (주소)
- **직접 눈으로 확인해야 하는 것** — 자동 검증으로 못 잡는 것들
- 요청 중에 하지 못한 부분과 그 이유

## 하지 말 것

- 요청을 임의로 넓히거나 줄이지 않는다. 범위를 바꿔야 한다고 판단하면 먼저 말한다
- 확인받지 않은 추측으로 구현하지 않는다
- QA 를 건너뛰고 완료라고 하지 않는다
- 비개발자에게 코드 조각이나 파일 경로를 늘어놓지 않는다 — 필요하면 별도로 정리해 준다
